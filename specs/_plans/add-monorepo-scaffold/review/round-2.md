## Feasibility

Dependency versions carried over from round 1 are unchanged and were confirmed there. `typescript@6.0.3` and Node `22.23.2` were both exercised directly in this round. The findings below concern the two packages whose task bodies changed.

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: plan.md § Dependencies, `@types/node` row; plan.md § Implementation Tasks, tasks 9 and 10
- Issue: `@types/node` is scoped to "`server`, root tests" and task 9 gives `packages/web` no `types: ["node"]` — the asymmetry is deliberate, since task 12 sets it for `server` alone. Task 10 then requires `packages/web/src/build.test.ts` to drive Vite's programmatic `build()` "into a temporary `outDir`, asserting the emitted `index.html` exists". Creating a temporary directory and reading the emitted file requires `node:os` and `node:fs`, and `platform/web-shell/spec.md` § "Production build emits a loadable bundle" mandates the on-disk form ("the output directory MUST contain an `index.html`"), so the in-memory `write: false` escape is closed. Under pnpm's isolated `node_modules`, `packages/web/node_modules/@types/node` will not exist — `@types/node` is a devDependency of `vite`, not a runtime one — so `import { mkdtemp } from 'node:fs/promises'` in the test source raises TS2307. `skipLibCheck` does not help: the failure is in a `.ts` source file, not a `.d.ts`. Two Checklist rows therefore fail as written — "Typecheck | `pnpm typecheck` | Exit 0" and "Lint | `pnpm lint` | 0 errors, 0 warnings".
- Fix: Change the `@types/node` row in plan.md § Dependencies to scope `server`, `web`, root tests. Add `types: ["node"]` to the `packages/web` `tsconfig.json` description in task 9, matching task 12's server config. State in task 10 that `build.test.ts` creates its output directory with `node:os` `tmpdir()` plus `node:fs/promises` `mkdtemp` and reads the emitted `index.html` back with `node:fs/promises`. While editing § Dependencies, add `@testing-library/dom` at `^10.4.1` scoped to `web`: `@testing-library/react@16` declares it as a peer rather than bundling it, and pnpm's isolated layout makes an undeclared peer a resolution risk.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Implementation Tasks, task 15; plan.md § Verification § Checklist, "Test" row
- Issue: Task 1 sets the root `test` script to `vitest run`, and task 15 adds "root `tests/workspace.test.ts` and its `vitest.config.ts`" without stating that config's `include`. Vitest's default `include` is `**/*.{test,spec}.?(c|m)[jt]s?(x)`, which from the repository root also matches every co-located package test. The Checklist's `pnpm -r --include-workspace-root test` runs the root script, so by default `App.test.tsx` executes a second time under the root config with no `jsdom` environment and fails, `build.test.ts` runs a second full Vite build, and the `*.test-d.ts` files are silently skipped because `typecheck.enabled` is not set there. The Checklist's "0 failures across all four suites" presumes exactly four suites; the default configuration produces overlapping ones.
- Fix: State in task 15 that the root `vitest.config.ts` sets `include: ['tests/**/*.test.ts']` and `environment: 'node'`, so the root suite covers only `tests/` and never re-runs a package's co-located tests.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Implementation Tasks, tasks 9 and 10
- Issue: Task 9 gives `packages/web` a single `vitest.config.ts` "with the `jsdom` environment", which applies to every test in the package. Task 10's `build.test.ts` then runs a full Vite production build inside that environment. jsdom installs `window`, `document`, and its own `performance` and `crypto` globals into the process, which is the environment Vite's build path branches against; the two tests in this package want opposite environments, and only `App.test.tsx` needs the DOM.
- Fix: State in task 10 that `packages/web/src/build.test.ts` opens with the docblock `// @vitest-environment node`, overriding the package default for that file alone, and note in task 9 that the `jsdom` default exists for `App.test.tsx`.

#### [AMBIGUOUS_REQUIREMENT] ADVISORY
- Location: plan.md § Design § Key interfaces, supporting-types line; plan.md § Implementation Tasks, task 6; decision-log.md § Design Decisions [6]
- Issue: `ResponseSchema` is listed as a supporting type and task 6 instructs the implementer to "document it as a declarative description of the required response structure", but no artifact states its shape. `platform/core-ports/spec.md` § "LlmPort returns a whole response for structured requests" constrains only its optionality ("the request type MUST accept a response shape without requiring one"), which `ResponseSchema = unknown` satisfies. If no shape can be committed to at scaffold time, delete `ResponseSchema` from § Key interfaces and task 6, drop the "*AND* the request type MUST accept a response shape without requiring one" clause, and record the deferral in decision [6].

#### [COMPLETENESS_GAP] ADVISORY
- Location: plan.md § Implementation Tasks, task 16; specs/mission.md § Commands; decision-log.md § Design Decisions [10]
- Issue: Task 16 is correctly scoped — it edits three named statements in `specs/mission.md` and nothing else — but it leaves § Commands stale in the same way. The mission documents `pnpm -r test` and `pnpm typecheck`; neither reaches `tests/workspace.test.ts`. `pnpm -r test` omits the workspace root by definition, and root `typecheck` is `pnpm -r typecheck`, which delegates to the three packages. Nine of the plan's 28 Scenario Coverage rows live in that root suite, so a contributor following the mission's own cheatsheet verifies two-thirds of the scenarios and no root TypeScript at all. Decision [10] notes the difference is "documented in the Checklist", which is the plan artifact `/speq:record` archives rather than the one it leaves behind.

## Task Breakdown

#### [TRACEABILITY_GAP] BLOCKER
- Location: plan.md § Implementation Tasks, task 8; plan.md § Verification § Scenario Coverage, row "Ports are reachable from the package entry point"; `platform/core-ports/spec.md` § Scenario "Ports are reachable from the package entry point"; decision-log.md § Review Findings [9]
- Issue: Task 8 specifies "type-level assertions covering the entry point's re-exports via `expectTypeOf<typeof import('@chrysalyst/core')>`". `typeof import(...)` produces the type of the module's namespace *object*, whose members are its value exports; `export type` and `export interface` declarations are not members of it. `@chrysalyst/core` is types-only by construction, so that type is `{}` and no `expectTypeOf` assertion against it can observe `LlmPort`, `SearchPort`, `SessionStorePort`, `ClockPort`, or `CoreDependencies`. Verified with `tsc@6.0.3` under this plan's exact option set: for a module exporting one runtime constant plus type-only declarations, `keyof typeof import('./index.ts')` contained the constant alone, and assigning a type name to it failed with `error TS2322: Type '"ClockPort"' is not assignable to type 'never'`. The spec scenario is sound — it asks that the entry point export the types — but the only task mapped to it implements an assertion that cannot pass. This is round-1 BLOCKER [TRACEABILITY_GAP] relocated from runtime to a `typeof` type query, not fixed.
- Fix: Replace the `typeof import('@chrysalyst/core')` clause in task 8 with an indexed-access form that reaches type-only exports — for each of `LlmPort`, `SearchPort`, `SessionStorePort`, `ClockPort`, `CoreDependencies`, and every supporting type, alias it as `type X = import('@chrysalyst/core').X` and assert it with `expectTypeOf<X>()` against a conforming object literal. Verified working: `type Clock = import('@chrysalyst/core').ClockPort` type-checks against a types-only entry point resolved through `exports`. Add a sentence to decision-log § Review Findings [9] recording that `typeof import(...)` sees value exports only, so the assertion form is an indexed type reference rather than a namespace query.

## Design Depth

No objection — axis checked. Dependency direction verified across all three manifests: `core` declares no `dependencies`, `server` declares `@chrysalyst/core` at `workspace:*`, `web` declares neither, and `platform/monorepo-workspace/spec.md` and `platform/http-server/spec.md` each assert one half of the acyclicity. `CoreDependencies<TState>` gives decision [8] a home in the type system rather than in prose alone, which is what the round-1 advisory asked for, and it stays a declaration with no body. `SessionStorePort<TState>` still refuses to guess the session model, `AbortSignal` remains a platform primitive, and the omission of `delete` is argued from the mission rather than from convenience.

One consequence is disclosed rather than hidden and is therefore not raised as a finding: under source resolution, `build` for `core` and `server` aliases `pnpm run typecheck`, so the Checklist's "Build" and "Typecheck" rows run the identical command for two of three packages. Decision [4] states this ("a `build` script that emits nothing for two of three packages"), and `platform/monorepo-workspace/spec.md` requires the script to exist, so the redundancy is deliberate.

## Requirement Quality

#### [COMPLETENESS_GAP] BLOCKER
- Location: `plan.md` § Requirements → Save failure; `adapters/filesystem-session-store/spec.md` § Scenarios, `A save that fails leaves the previous revision loadable`; `plan.md` task 2
- Issue: the save-failure guarantee is stated without bound, the design cannot deliver it at one failure point, and neither named injection reaches the behaviour the row adds.

  **The bound.** Walk the revised sequence — serialise, `mkdir`, write tmp1, write tmp2, rename tmp1 → `session.json`, rename tmp2 → `transcript.md`. The first four failure points commit nothing and the previous revision survives intact. The last does not: once `session.json` is renamed into place, a failed second rename (or a process death between the two) leaves the **new** `session.json` beside the **previous** `transcript.md`, and `load` answers the second revision. § Requirements § Save failure asserts the opposite without qualification — "The session directory is then left holding exactly what the previous successful save committed, and no temporary file." No implementation can satisfy that sentence without rollback machinery this plan neither designs, budgets, nor gives a scenario. The plan also contradicts itself: decision `[4]` calls a lagging transcript "ordinary", and § Requirements § Write order picks `session.json`-first rename precisely so the residue is that ordinary lag rather than the "lie" — so § Requirements § Save failure forbids the exact state decision `[4]` licenses.

  **The evidence.** Both injections task 2 names stop before the first temporary file exists. A `TState` holding a `BigInt` fails at serialisation, before any filesystem call. `chmod(dir, 0o500)` fails the **first** `writeFile` with `EACCES` and — verified — leaves no file in the directory. Two consequences follow. First, both injections behave identically under the design this revision replaced (write tmp1 → rename → write tmp2 → rename), so the scenario passes unchanged against the old ordering and no test in the plan can detect whether two-phase staging was implemented at all. Second, the scenario's clause "so the failed save removed every temporary file it created" and § Requirements' cleanup rule ("removes every temporary file it created with `rm(path, { force: true })`… A cleanup that itself fails MUST NOT replace the original rejection") are never exercised, because neither injection creates a temporary file. That cleanup rule is load-bearing: `rm(existing, { force: true })` in a `0o500` directory rejects `EACCES`, so an implementation that awaits cleanup unguarded replaces the rejection that names the fault. No real-filesystem injection closes this — the only rename that can fail while leaving `session.json` loadable is the first, and it fails only when `session.json` is a directory, which makes the previous revision unloadable and breaks the scenario's `GIVEN`.
- Fix: Four edits. (1) In `plan.md` § Requirements § Save failure, replace "The session directory is then left holding exactly what the previous successful save committed, and no temporary file" with two bounded sentences: "A failure at or before the rename of `session.json` leaves the session directory holding exactly what the previous successful save committed, and no temporary file. A failure of the `transcript.md` rename leaves the new `session.json` beside the previous `transcript.md` — the lagging derived view decision `[4]` accepts — and never the reverse." (2) In `adapters/filesystem-session-store/spec.md`, tighten the `WHEN` of `A save that fails leaves the previous revision loadable` to "a second save of the same identifier fails before either file is renamed into place, either because the state cannot be serialised or because the session directory refuses the write", so the scenario's scope matches the injections that prove it. (3) Add a `plan.md` § Consequences row — Decision "A failed second rename is not undone", Alternatives "Restoring the previous `session.json` from a backup copy", Rationale naming the residual window and why the `session.json`-first rename order makes its residue the lag decision `[4]` already accepts — and restate decision `[5]` § Rationale to claim a narrowed window rather than an eliminated one. (4) In `plan.md` task 2, add a third injection that reaches the cleanup path: `vi.mock('node:fs/promises', importOriginal)` rejecting the **second** `writeFile` call, asserting `save` rejects with that error, the previous revision still loads, and the session directory holds no `*.tmp` entry. If the plan declines fault injection at the `fs` layer, state that decision in § Verification and soften the § Patterns claim "No test needs a mock filesystem" to say the cleanup path and the staging order rest on reasoning rather than on a test.

# Decision Log: single-question-walking-skeleton

## Interview

**Q:** What exactly does the one round do?
**A:** The LLM asks a question, the user answers, done. A hardcoded system prompt makes the model phrase one opening question and stream it. The user types an answer. Question, answer and timestamps are persisted. No second turn, no acknowledgement or distillation streamed back.

**Q:** What shape does `TState` v1 take — the session state in `core` that the store persists, which grows over M8, M9 and M14?
**A:** A turn list. `{ turns: readonly Turn[] }` where a `Turn` carries `question`, `answer`, `askedAt` and `answeredAt`. A list from v1 even though M3 only ever puts one element in it, so it grows into the multi-round interview of M8 without a schema break. ISO strings rather than `Date`, because the filesystem session store revives only its own two envelope timestamps and `TState` must survive a JSON round trip — the constraint recorded in `adapters/filesystem-session-store` as `State the store cannot serialise does not survive the round trip`. The envelope's `schemaVersion` stays `1`: it versions the envelope, not the domain session. This plan chooses the `TState` the envelope wraps.

**Q:** What shape does the HTTP and SSE contract take? The SSE event contract is an explicit M3 decision.
**A:** A session resource with separate routes. `POST /interview` creates a session and returns `{ id }`. `GET /interview/:id/question` is an SSE stream carrying `token` events with `{ text }`, a `done` event carrying the full question text, and an `error` event with `{ message }`. `POST /interview/:id/answer` accepts `{ answer }` and returns 204. Exact naming may be refined within that shape. Use Hono's `streamSSE`. Decide and document whether the question is generated once and persisted on first `GET` or regenerated per connection; prefer generated and persisted once, so a reconnect replays the stored question rather than calling the model again.

**Q:** Which language does the hardcoded system prompt and opening question use in M3, given that M5 is where the DE/EN bilingual foundation lands?
**A:** English. Hardcoded English system prompt, English interface strings. Small local models are often stronger in English, which better supports the feasibility claim. M5 externalises DE and EN.

**Q:** How far does live verification go? M3 wants a feasibility note — model, time to first token — in the verification report, and the guardrails want live-tagged tests.
**A:** A live end-to-end test plus a manual `pnpm dev` run. A `*.live.test.ts` drives the real flow and measures time to first token; the manual browser run produces the feasibility note. Model `qwen3:8b`, because `llama3.2:3b` is not pulled on this host and the M1 live test already runs against `qwen3:8b` through the `CHRYSALYST_LLM_MODEL` override. The live file follows the convention `tests/workspace.test.ts` checks: `describe.skipIf((process.env.CHRYSALYST_LIVE_LLM ?? '') === '')` and no module-scope `await`. Invoked as `CHRYSALYST_LIVE_LLM=1 CHRYSALYST_LLM_MODEL=qwen3:8b pnpm -r --include-workspace-root test`. Hermetic tests — a fake `LlmPort` yielding fixture chunks, a real filesystem through `mkdtemp` — stay the primary substrate and must cover the whole flow.

**Q:** How much design investment does the first UI get?
**A:** A full impeccable subphase, sequenced after the technical planning. The planner produces routes, `TState`, the use case, tests and the composition root first; the orchestrator then runs impeccable as a separate subphase and merges the approved comp reference into `plan.md` before the adversarial plan review. `plan.md` therefore carries a marked placeholder section for the design direction and a task for implementing the approved styling, and the planner invents neither the visual design nor the styling stack. `decision-log [14]` of `001-add-monorepo-scaffold` deferred the styling-stack choice to this first UI feature; that choice becomes an ADR here and comes out of the impeccable subphase.

## Design Decisions

### [1] `InterviewState` v1 is a turn list over a tagged union

- **Decision:** `InterviewState = { turns: readonly Turn[] }`, with `Turn = AskedTurn | AnsweredTurn` as two closed shapes, each carrying a literal `status` — `'asked'` or `'answered'` — and `isAnswered` narrowing on that tag. Every instant is an ISO 8601 string. The store's envelope `schemaVersion` stays `1`, and the transcript is not versioned at all.
- **Alternatives:** The interview's literal answer — one `Turn` with all four fields required — rejected because it cannot represent the state the same interview requires between the question being stored and the answer arriving, which is the state a reconnect replays from. One `Turn` with `answer` and `answeredAt` optional — rejected because it admits an answer with no `answeredAt`, a combination that means nothing. An untagged union with `AnsweredTurn extends AskedTurn`, narrowed by `'answer' in turn` — rejected once round 1 showed it delivers neither half of that argument: an `AskedTurn` literal carrying a stray `answer` is assignable to the union, and so is an `answeredAt` with no answer. A single `question`/`answer` pair with no list — rejected because M8 would then break the schema on its first turn.
- **Rationale:** The list is the interview's answer and costs nothing at one element. The two shapes are what the generate-once requirement forces: the question is durable before the answer exists, so "asked but unanswered" is a real state and the type should say so. The tag is what makes that claim true rather than decorative — it is the only form in which TypeScript actually excludes the mixed literals, and it is also the only form that still narrows after a JSON round trip, since a loaded turn arrives as plain data with no class to check against. ISO strings are not a preference either: the store hands `state` back exactly as `JSON.parse` produced it, so a `Date` field would type as `Date` and arrive as `string`. `schemaVersion` is untouched because `002`'s ADR `schemaversion-versions-the-on-disk-envelope` already settled that it versions the envelope and not the domain state inside it.
- **Promotes to ADR:** yes

### [1a] `@chrysalyst/core` renders the transcript; the store takes the renderer as optional config

- **Decision:** `packages/core/src/interview/transcript.ts` exports a pure `renderTranscript(session: StoredSession<InterviewState>): string`. `FilesystemSessionStoreConfig` takes a defaulted type parameter and accepts an optional `renderTranscript?: (session: StoredSession<TState>) => string`; `save` hands the renderer its own argument when one is configured and falls back to today's metadata header when not. `createDependenciesFromEnv` passes core's renderer by reference. The transcript carries no version.
- **Alternatives:** Rendering the Markdown inside the store — rejected because the store's recorded boundary is that it "never interprets `TState`", and `003`'s ADR `schemaversion-versions-the-on-disk-envelope` rests on that. Leaving `transcript.md` a metadata stub and moving the roadmap's promise to a later milestone — rejected by the user: `specs/roadmap.md` § M2 deferred the interview content to M3 verbatim, and M6 needs a transcript that renders. Making the renderer required — rejected because it would force every future non-interview `TState` to supply one and would break `003`'s recorded scenarios.
- **Rationale:** The Markdown shape is a fact about the interview, so it belongs where the state's owner lives; when the file is written is a fact about the store, so that stays the store's. Optionality is what keeps the change additive: the three `003` scenarios that assert the header and the failed-save behaviour stay green untouched, which is the evidence that the boundary held. The defaulted type parameter is the other half of that additivity — without it `sessionStoreConfigFromEnv`'s declared return type stops compiling. The renderer takes `StoredSession<TState>`, the port's own type, rather than a purpose-built triple of its fields: one concept keeps one name, the store passes `save`'s argument straight through, and the composition root wires the function by reference with no adapting lambda. A renderer that throws travels the store's existing staging path, so a bad render leaves the previous revision loadable rather than half-written.
- **Promotes to ADR:** yes

### [2] The SSE contract is three event types, single-line JSON payloads, and no event id

- **Decision:** `token` carries `{ text }`, `done` carries `{ question }`, `error` carries `{ message }`. Every `data` field is one line of JSON. No `id:` field and no reconnection protocol. `done` is written only after the question is stored, so observing `done` means the question is durable.
- **Alternatives:** Raw text in `data` with no JSON envelope — rejected because a model chunk containing a newline would split one frame into two and there is no way to tell that apart from a frame boundary. `id:` plus `Last-Event-ID` resumption — rejected as a protocol with no requirement behind it: a client that loses the stream re-requests it and receives the stored question, which is simpler and already needed. A single event type with a `type` field inside the payload — rejected because SSE already has an event channel and a client should be able to route on it.
- **Rationale:** `JSON.stringify` escapes a newline, so the JSON envelope is what makes the framing total rather than probabilistic; the plan asserts it as `Token text carrying a newline stays inside one frame`. Ordering `done` after the save turns durability into something a client can observe rather than assume, and it is what makes generate-once free: the first request stores, every later one replays.
- **Promotes to ADR:** yes

### [3] The interview is a factory over `CoreDependencies` returning three operations, and it answers absence rather than throwing

- **Decision:** `createSingleTurnInterview(deps)` returns `begin`, `openingQuestion` and `recordAnswer`. `openingQuestion` resolves `AsyncIterable<string> | undefined`, resolving before the model is reached. `recordAnswer` resolves `'recorded' | 'no-session' | 'no-open-question'`, and `'no-open-question'` covers an empty turn list as well as an already-answered last turn — a session whose question was never requested has nothing to answer. `begin` never overwrites: an identifier that already holds a session is left as it stands, so a repeated call cannot replace a stored question and answer with an empty list. The module lives at `packages/core/src/interview/`, the first application code in the package.
- **Alternatives:** Three free functions each taking `deps` — rejected because every route handler would then repeat the plumbing and there would be no single place to state the module's design intent. Returning a bare `AsyncIterable` from `openingQuestion` — rejected because the route must answer `404` before it opens an SSE stream, and a bare iterable pushes that decision into iterator mechanics at the call site. Typed error classes for the two refusals — rejected because a stale link and a resubmitted form are ordinary outcomes, and a three-member union is smaller than a hierarchy. Keeping the use case in `packages/server` until M7 — rejected because it inverts the architecture on the first feature that has any domain logic at all.
- **Rationale:** The split between resolving the stream and pulling from it is the whole reason the shape is a `Promise` of an iterable: the load decides existence, the pull reaches the model, and a refused request infers nothing. The outcome union speaks the domain's vocabulary and lets the route own the mapping to `404` and `409`, so no status code appears in `core`. `undefined` for absence deliberately mirrors `SessionStorePort.load`, which the same caller already reads.
- **Promotes to ADR:** yes

### [4] `packages/web` keeps no dependency on `@chrysalyst/server` and restates the wire shapes

- **Decision:** No `hc<AppType>` client in `web`, and no type-only package edge. `web` reads the stream with `fetch` and a `ReadableStream`, declares the three wire shapes itself, and treats `interview/interview-http-api` as the shared contract both packages' tests are written from. `tests/fixtures/interview-sse-frames.txt` is that contract's executable half: one file of literal SSE bytes outside both packages, which the route test asserts the server emits and the parser test consumes, so a rename on either side fails a run instead of a browser. `client.test-d.ts` stays in `server` and grows to cover the three new routes. `tests/workspace.test.ts` gains a scan asserting no file under `packages/web/src` imports a `@chrysalyst/` specifier, so the invariant fails a run rather than a review. This reverses a named deliverable: `specs/roadmap.md` § M3 "Liefert" promises an `hc<AppType>`-Client in `packages/web`, and `/speq:record` MUST replace that clause with the wire-shape restatement this plan ships.
- **Alternatives:** Adding `@chrysalyst/server` as a type-only dependency, which `decision-log [13]` of `001-add-monorepo-scaffold` explicitly deferred to "the first real feature" — this one. Rejected on the balance below. Using `EventSource` instead of `fetch` — rejected separately: it cannot be aborted with a signal the interview already threads through, and it makes the parser untestable at a chunk boundary.
- **Rationale:** `hc` types route paths and JSON bodies. It cannot type an SSE event name or its payload, which is the larger half of this contract and the half M3 exists to settle, so the edge would buy path names, `{ id }` and `{ answer }` while costing a browser package a type dependency on a Node package whose graph reaches `node:fs`, `ai` and `@ai-sdk/openai-compatible`, plus `hono` as a runtime dependency and two rewritten workspace invariants. The asymmetry that decides it is reversal cost: adding the edge later deletes three literal declarations, while removing it later means unpicking a `web` that has grown against it. The residual risk the first draft accepted — a rename on one side caught only by the manual browser run — is now largely closed by the shared frame fixture, at the cost of one file and no package edge; what remains uncovered is the two JSON bodies, which are three fields. Revisit at M11, whose live spec preview is the first wire shape too large to restate by hand. This decision does not contradict `001`'s ADR `hono-server-framework`, whose typed-client claim is still proved inside `server`; it declines to spend a package edge on the part of the contract the client cannot type.
- **Promotes to ADR:** yes

### [5] The app is built by a factory and the server is handed the app it serves

- **Decision:** `createApp(deps)` replaces the module-scope `app`, `AppType` becomes `ReturnType<typeof createApp>`, and `startServer(app, port, host?)` no longer imports `app.ts`. `main.ts` becomes the composition root: `createDependenciesFromEnv(process.env)` assembles the LLM adapter, the filesystem store and a system clock, and hands them to `createApp`.
- **Alternatives:** Keeping the module-scope app and reaching dependencies through a mutable holder set at boot — rejected as a hidden global that every route test would share. Constructing the adapters inside `app.ts` — rejected because a route test would then need a real Ollama and the user's home directory.
- **Rationale:** Concrete implementations are constructed only at the entry point, which is what makes a route test able to build an app over a fake model and a `mkdtemp` store. Deriving `AppType` from the factory rather than declaring it beside one removes the second place a route could be missing from. The cost is a delta on four `platform/http-server` scenarios, each of which names the old construction in its `GIVEN`.
- **Promotes to ADR:** yes

### [6] The question is generated on the first request for it, never at session creation

- **Decision:** `POST /interview` performs no inference and answers immediately. The model is reached on the first `GET /interview/:id/question`; the accumulated question is stored before the `done` event; every later request replays the stored text.
- **Alternatives:** Generating the question inside `POST /interview` — rejected because it blocks the create request on a whole inference and destroys the measurement this milestone exists to take. Regenerating per connection — rejected because a reload would then produce a different question from the one already on disk.
- **Rationale:** The milestone's purpose is time to first token in a browser. That figure is only meaningful if the stream request is the one that reaches the model. Storing before announcing gives generate-once with no extra state and no flag.
- **Promotes to ADR:** no

### [6a] One in-flight question per session, guarded process-locally

- **Decision:** `createSingleTurnInterview` holds a `Map<SessionId, Promise<string>>` in its closure. A request for a question that finds an entry awaits it and replays its result rather than reaching the model; the entry is deleted once the promise settles either way. A shared production owns its cancellation: the interview creates one `AbortController` per production and passes **its** signal to `LlmPort.stream`, never a caller's. A caller's own `signal` ends only that caller's iteration, and the controller is aborted only once every caller sharing the production has abandoned it, counted by reference. The shared promise resolves only after `save` resolved. The guard is process-local and the plan says so in § Key interfaces, § Requirements and § Impact.
- **Alternatives:** Leaving load-then-save uncoordinated — rejected: two overlapping requests both load an empty turn list, both reach the model, and the later save replaces a question a client already saw announced by `done`, which falsifies both "Generate once" and "Durable before announced" as written. Binding the shared production to the signal of whichever caller started it — rejected in round 2: the owner's abort then either truncates the waiting caller's question, so a reload shows different text than `done` announced, or rejects a production nothing actually failed. Letting the shared promise reject when its owner abandons, the reviewer's stated alternative — rejected for the same reason: it turns one caller's ordinary disconnect into another caller's `error` frame. A lock file or a compare-and-swap in the session store — rejected as machinery for a single-user localhost app, and `003` deliberately shipped no locking. Making the requirements conditional instead of adding the guard — rejected because the reload the plan's own § Manual Testing instructs is exactly the race.
- **Rationale:** The race is reachable, not theoretical: a server does not observe the old connection's close before the new request's load, so a mid-stream reload hits it. A closure-held map is the smallest mechanism that makes the requirement true, costs nothing when there is no contention, and adds no port and no dependency. Keeping an entry only while the promise is unsettled means a failed production does not poison the session. Sharing a production, however, means it can no longer belong to one caller — a reload is precisely one caller leaving while another arrives, so the guard would otherwise reintroduce the fault it was added to remove. An interview-owned controller with a reference count is what keeps every stated rule true at once: with one caller it aborts exactly when that caller abandons, which is today's behaviour unchanged; with two it survives the first leaving. Resolving the shared promise only after `save` is the matching rule on the other side — it is what lets the second caller's `done` mean durable, not just "text arrived". The honest limit is that two processes over one session directory can still double-generate; one process is what `pnpm dev` and the entry point run, and no milestone before M17 introduces a second.
- **Promotes to ADR:** no

### [7] Nothing partial is ever stored, and an abandoned stream is not a failure

- **Decision:** A question is stored only when the model's stream ended of its own accord and the accumulated text is not blank. An aborted request stores nothing and does not reject; a rejected model stream propagates unchanged and stores nothing; a blank result rejects and stores nothing.
- **Alternatives:** Storing chunks as they arrive so a dropped connection keeps partial progress — rejected because a half-question is not a question and a reconnect would replay it forever. Treating an abort as an error — rejected because it contradicts the adapter's recorded behaviour.
- **Rationale:** The abort half follows `decision-log [6]` of `002-add-ollama-llm-adapter`, where an aborted `stream` ends quietly because tearing down a socket mid-answer is the caller's own doing. The blank-result half exists because a model that answers with whitespace would otherwise produce a session whose stored question is empty and whose replay is empty forever, with no failure anywhere to explain it.
- **Promotes to ADR:** no

### [8] The session identifier is minted by the route, not by the domain

- **Decision:** The create route calls `randomUUID()` and passes the identifier into `begin(id)`. `CoreDependencies` gains no fifth port.
- **Alternatives:** An `IdPort` beside `ClockPort` — rejected as a port added for one call site, which would need a delta on `platform/core-ports-contract`, a new port spec, and an adapter, all for a single `randomUUID`. Calling `crypto.randomUUID()` inside `core` — rejected because randomness is ambient nondeterminism exactly like the system clock, and the package's whole point is that it reads neither.
- **Rationale:** The store already owns which identifiers can exist — `decision-log [6]` of `003-add-filesystem-session-store` made the single-path-segment rule the store's — so the identifier is already an adapter-side concern. Passing it in keeps the domain deterministic at no cost. If a second driving adapter ever needs to mint one, an `IdPort` is the change, and it is small.
- **Promotes to ADR:** no

### [9] The specs are cut into three interview features in a new `interview/` domain, plus three deltas

- **Decision:** New domain `interview/` with `single-question-interview` (the domain rules, `InterviewState` and the transcript rendering), `interview-http-api` (the routes, the SSE contract and the composition root) and `interview-view` (what the person perceives and can act on). `platform/http-server`, `platform/web-shell`, `platform/core-ports-contract` and `adapters/filesystem-session-store` each take a delta.
- **Alternatives:** One feature covering all three layers — rejected because the three have different reasons to change: M8 changes the wire contract, the impeccable subphase and M5 change the view, and M7 changes the domain rules. Adding the features to `platform/` — rejected because `platform/` holds eight features and `/speq:record` stops for a human past eight, the same constraint that created `adapters/` in `decision-log [8]` of `002-add-ollama-llm-adapter`. Folding the view into `platform/web-shell` — rejected as stuffing interview behaviour into a platform feature to dodge that limit; `web-shell` keeps only what is genuinely the shell's, namely the build, the mount and the no-internal-dependency rule.
- **Rationale:** Grouping by reason to change is the same rule that produced `adapters/`, and it lands the three features where the milestones that will edit them can find them. The three deltas are each forced rather than chosen: `http-server`'s four scenarios name a construction this plan replaces, `web-shell`'s placeholder screen is deleted by this plan, and `core-ports-contract`'s background says the package holds type declarations only, which stops being true the moment `core` gains a use case. `core-ports-contract`'s existing scenarios all stay true, so its delta changes the background and adds one scenario rather than rewriting `Core carries no runtime dependency`: that scan reads import specifiers, not exports, and so already permits domain code that depends on nothing.
- **Promotes to ADR:** no

### [10] Styling stack — plain CSS with a custom-property token layer plus CSS Modules

- **Decision:** `packages/web` styles with hand-written CSS: one token layer as `:root` custom properties (the table in `plan.md` § Design Direction — five colours, two font families, one measure, the micro-label recipe) and one `*.module.css` file per component, scoped by Vite's native CSS Modules. No CSS framework, no component library, no CSS-in-JS runtime. Source Serif 4 and Libre Franklin are self-hosted under `packages/web` and loaded with `@font-face`, never from a CDN. This settles `decision-log [14]` of `001-add-monorepo-scaffold`, which deferred the choice to this first UI feature's impeccable subphase.
- **Alternatives:** Tailwind — rejected: the editorial system is a small fixed set of tokens (two faces, five colours, hairline rules, one column), and utility classes scatter that system across markup while adding a PostCSS/Tailwind build step and a config file to a package that has neither. CSS-in-JS (vanilla-extract, styled-components) — rejected: a runtime or a compiler plugin for a surface this small, and the token layer is exactly what plain custom properties express. A single global stylesheet with BEM naming — rejected: co-locating each component's styles as a module keeps the cascade shallow and the scope automatic without a naming discipline to enforce.
- **Rationale:** The impeccable direction is "hairline rules and space, no cards, no shadows" — a system whose whole surface area is the token table. Custom properties make that layer explicit and one place to change; CSS Modules give per-component scope with zero runtime cost and no new toolchain, and Vite already resolves them. The choice also keeps M5's locale work and any future dark mode as edits to the `:root` token block rather than a framework migration. The cost is that responsive and state styling are written by hand rather than composed from utilities, which for one column and six states is a few dozen lines.
- **Promotes to ADR:** yes

### [11] C2 is skipped again, and M3 stays open when this plan records

- **Decision:** Proceed without the minimal CI pipeline (C2), as `decision-log [9]` of `002-add-ollama-llm-adapter` did. `/speq:record` MUST leave milestone M3 at `⬜ offen` in `specs/roadmap.md` § Überblick, and this plan edits no roadmap status.
- **Alternatives:** Building C2 first — deferred again by the same standing instruction. Flipping M3 to done on record — rejected because M3 names two plans and the second, `engine-structure-spike`, still owes the throwaway turn-loop comparison and the ADR-ready note on the M7 engine structure.
- **Rationale:** The consequence of skipping C2 is unchanged and now larger. Only a local run enforces the § Verification checklist, nothing proves the suite green on a clean machine, and the live tier's behaviour on a machine without Ollama stays unproven until M4 — while this plan adds a second file to that tier. Stating it here means M4 inherits a known debt rather than discovering one.
- **Promotes to ADR:** no

## Review Findings

### [1] [plan-review] The transcript still held no interview

- **Finding:** `[SCOPE_REDUCTION]`, round 1. `specs/roadmap.md` § M2 defers the transcript's interview content to this milestone verbatim, and no task, scenario, or Non-Goal in the plan mentioned `transcript.md`. The store's `toTranscript` writes an identifier and two timestamps, so the file would still have carried no question and no answer after M3 — while § Impact already claimed a person could read it. The omission also hid a design question: the store's recorded boundary says it never interprets `TState`, so the rendering could not simply move into it.
- **Direction change:** The user chose to honour the M2 promise here. `@chrysalyst/core` gains `interview/transcript.ts`, a pure `renderTranscript(state, meta)`; `FilesystemSessionStoreConfig` becomes generic and accepts an optional renderer, falling back to the existing header when none is configured; `createDependenciesFromEnv` supplies the interview's. New delta `adapters/filesystem-session-store` carries one changed and two new scenarios, plus tasks 5, 11 and 12, the § Verification rows, a § Goals bullet, a § Requirements row, a § Migration row, a § Consequences row, and decision `[1a]`. § Impact now states what the file holds. The transcript stays unversioned, so `002`'s ADR `schemaversion-versions-the-on-disk-envelope` is untouched.
- **Promotes to ADR:** yes

### [2] [plan-review] The dropped `hc` client was invisible to the roadmap

- **Finding:** `[INTENT_DRIFT]`, round 1. `specs/roadmap.md` § M3 "Liefert" names an `hc<AppType>`-Client in `packages/web` as a deliverable. The plan ships none, restates the wire shapes by hand, and adds a workspace invariant that would fail one — argued at length, but neither § Consequences nor decision `[4]` named the roadmap line being reversed or proposed amending it. After `/speq:record` the roadmap would still promise a client the recorded specs forbid.
- **Direction change:** The user confirmed the deviation, so the technical decision stands unchanged. § Impact gains a paragraph naming the reversal and an instruction that `/speq:record` MUST replace § M3 "Liefert"'s client clause with the wire-shape restatement this plan ships, beside the existing instruction to leave M3 open. Decision `[4]` and § Consequences row 1 carry the same sentence.
- **Promotes to ADR:** no

### [3] [plan-review] The abort test aborted nothing

- **Finding:** `[UNSTATED_ASSUMPTION]`, round 1. Task 6 specified asserting abandonment by aborting an `AbortSignal` passed to `app.request`. In `hono@4.13.7`, `streamSSE` subscribes to `c.req.raw.signal` only under `isOldBunVersion()`; on Node `StreamingApi.abort()` runs only from the response body's `cancel` callback. The reviewer measured it against the installed packages: the signal left `onAbort` unfired and all chunks produced, while `reader.cancel()` fired it after one. That test was the only automated coverage of `A client that abandons the question stream stores nothing` and of decision `[7]`, so it would have failed while the code under test was correct.
- **Direction change:** Task 8 now cancels through the response body — read `response.body` with a reader, consume the first `token` frame, call `reader.cancel()` — and forbids the signal form. Task 9 states that `onAbort` is reached through body cancellation, which is what `@hono/node-server` triggers on client disconnect, and that `c.req.raw.signal` must not be subscribed. The `interview/interview-http-api` scenario's `WHEN` now reads "stops reading the response body", its § Background explains the mechanism, and § Dependencies repeats it.
- **Promotes to ADR:** no

### [4] [plan-review] Two overlapping question requests both reached the model

- **Finding:** `[NFR_IGNORED]`, round 1. § Requirements stated "the model is reached at most once per session" and "a client that observed `done` and reloads MUST see the same question" absolutely, and the design had no mechanism holding either under concurrency. Load-then-save lets two overlapping requests both load an empty turn list, both infer, and both save, so the later save can replace a question a client already saw announced. The plan's own § Manual Testing instructs the reload that races it. `<StrictMode>` compounded a smaller version in dev by creating one orphan session per page load, unmentioned.
- **Direction change:** Task 4 specifies a process-local `Map<SessionId, Promise<string>>` in the factory's closure, awaited by a concurrent request and deleted once settled. New scenario `Two concurrent requests for the opening question reach the model once`, covered by task 3 with a gated model double, plus its § Verification row and a § Manual Testing row driving two overlapping `curl` requests. § Key interfaces, § Requirements and § Impact all state that the guard is process-local and that two processes over one directory can still double-generate. The `pnpm dev` row now names the `<StrictMode>` orphan directory. Decision `[6a]` records it. Answer submission needs no guard: the second of two overlapping submissions finds an answered turn and is refused.
- **Promotes to ADR:** no

### [5] [plan-review] The untagged union excluded neither bad literal

- **Finding:** `[AMBIGUOUS_REQUIREMENT]`, round 1. ### [9] [plan-review] The fix for the race reintroduced the race

# Plan Review Findings: add-filesystem-session-store (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 15 (Blockers: 3, Advisory: 12)
- Intent Fidelity blockers: 0

## Premortem

Three failure stories, each routed into the taxonomy below.

**1. The silent session loss.** M17 ships the session library. A user's machine loses power during `save`. `session.json`'s directory entry is committed; its data block is not. Every later `load('sess-42')` rejects forever and `list()` omits the identifier without a word. The user sees the session vanish — exactly the outcome decision-log `[1]` claims to prevent ("the user would lose work without a message") and decision-log `[5]` claims write-then-rename removes. → Feasibility `[UNSTATED_ASSUMPTION]`, Requirement Quality `[COMPLETENESS_GAP]`.

**2. The clause that proved nothing.** M3 picks `TState` with a `Date` field. Its implementer reads the port's new clause — "a second double that stores the session through a serialisation round trip MUST return the same domain state" — as a guarantee the store preserves state, because that is what the sentence says and because the test passes. Runtime returns a string. → Requirement Quality `[AMBIGUOUS_REQUIREMENT]`.

**3. The unrecorded contract change.** M3 calls `load` on the port's documented promise that "a stale link is an ordinary outcome, not a failure", does not wrap the call, and an unhandled rejection reaches the HTTP route the first time a `session.json` is malformed. Nothing in `platform/session-store-port` told M3 that `load` can now reject. → Requirement Quality `[COMPLETENESS_GAP]`.

## Feasibility

No objection to the toolchain claims — axis checked, and every § Dependencies row I could execute reproduced: `zod@4.5.4` is installed under `packages/server/node_modules`; `z.unknown()` rejects an absent `state` key with exactly the quoted message `expected nonoptional, received undefined`; `z.iso.datetime()` accepts `toISOString()` output and rejects `2026-02-31T00:00:00.000Z`, `2026-02-30…` and `2026-04-31…` (calendar-validating, so the claim is stronger than stated); Node is `v22.23.2`; `node --input-type=module -e "await import('./packages/server/src/…ts')"` from the repo root both imports a `.ts` file and resolves `zod` from `packages/server/node_modules`. The `002-add-ollama-llm-adapter` roadmap-correction precedent is real (its task 8, § Impact line 115). These were executed, not recalled.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: `plan.md` § Design → Goals and § Consequences ("Write-then-rename for both files"); `decision-log.md` `[5]`
- Issue: the plan promises "a crash during `save` that cannot destroy the previous revision" and argues the mechanism removes a "total" failure mode. Write-then-rename delivers that for a **process** crash only. Nothing calls `fsync` on the temporary file before `rename`, and nothing calls `fsync` on the containing directory after it, so a power loss or kernel panic can still leave a zero-length or partially-written `session.json` under the committed name — which decision `[1]` then rejects on every subsequent `load`, permanently. The plan never states which crash class it covers, and § Dependencies verifies `rename` replaces the target without verifying anything about durability.
- Fix: In `plan.md` § Consequences, change the "Write-then-rename for both files" row's Rationale to scope the guarantee explicitly to a process crash, and add one sentence naming the residual power-loss window. Either add an `fsync` of the temporary file handle before `rename` to § Requirements § Atomic write, or record in `decision-log.md` `[5]` § Alternatives that `fsync` was considered and declined, with the reason.

#### [NFR_IGNORED] ADVISORY
- Location: `plan.md` § Requirements → On-disk layout; § Impact
- Issue: session folders hold a user's unreleased product ideas, and the plan never decides a file mode. `mkdir` and `writeFile` will use the process umask, so `~/.chrysalyst/sessions` and every `session.json` land world-readable (`0755`/`0644`) on a default Linux install. § Impact discusses the new environment variable and the untouched home directory but says nothing about who can read what the store writes.
- Fix: Add a § Requirements row "Permissions" fixing the mode of the root, each session directory, and both files (for example `mkdir(..., { recursive: true, mode: 0o700 })` and `mode: 0o600` on the writes), and add a clause to the `A saved session lands as a versioned JSON envelope` scenario asserting the mode. If the decision is to inherit the umask, record that as an explicit alternative in `decision-log.md` instead.

## Requirement Quality

#### [COMPLETENESS_GAP] BLOCKER
- Location: `platform/session-store-port/spec.md` § Scenarios; `plan.md` § Features
- Issue: this plan changes the `SessionStorePort` contract for every implementation and every caller — `load` may now reject — and records that change nowhere. The port delta touches only the round-trip scenario and the Background. After merge, `specs/platform/session-store-port/spec.md` still says of `load` only that "the port MUST resolve to `undefined`" and "the port MUST NOT throw" (scoped to an unknown identifier), and the port's own doc comment in `packages/core/src/ports/session-store.ts` says "Answers the stored session, or nothing when the identifier was never saved — a stale link is an ordinary outcome, not a failure." A reader of the port learns nothing about the rejection path. The Q2/Q4 asymmetry is coherent *inside* the adapter — one reader, two policies, one owner of the format — but it hides this gap at the boundary above it: `adapters/filesystem-session-store` makes rejection a MUST while `platform/session-store-port` still reads as a port that never throws. The same gap decides whether P1's hosted store must behave the same way, and nothing tells it.
- Fix: Add a `DELTA:NEW` scenario to `specs/_plans/add-filesystem-session-store/platform/session-store-port/spec.md` — `Scenario: A stored session the implementation cannot read is a failure` — asserting that a `SessionStorePort` implementation MUST reject `load` when the identifier's stored record is present but unreadable, that `undefined` is reserved for a record that was never saved, and that `list` MUST NOT reject over a record it cannot read. Extend `plan.md` task 5 to prove it with a third double in `packages/core/src/ports/ports.test.ts` whose backing map holds an unreadable marker. Amend the `load` doc comment in `packages/core/src/ports/session-store.ts` to state the rejection path, and relax the § Requirements "Port purity" row that currently forbids it — the workspace purity test (`tests/workspace.test.ts:297`) inspects only the manifest and import specifiers of non-test files, so a doc-comment edit keeps `platform/core-ports-contract` green.

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: `platform/session-store-port/spec.md` § Scenarios, `SessionStorePort round-trips a session`, final clause
- Issue: the clause "a second double that stores the session through a serialisation round trip MUST return the same domain state, because a store outliving a process returns only what its format preserved" cannot fail, and states the constraint backwards. Task 5 pairs it with the existing `DraftSpec` fixture (`{ title: string; answers: readonly string[] }`), which is JSON-safe, so `JSON.parse(JSON.stringify(...))` returns a deep-equal object by construction — the assertion is a statement about the fixture, not a requirement on any implementation. Make it bite by putting a `Date` in `TState` and the clause fails; so the only way to satisfy it is to choose a fixture that makes it vacuous. The real constraint runs the other way and is an obligation on the caller choosing `TState`, which the plan states correctly in `adapters/filesystem-session-store/spec.md` § Background and in `plan.md` § Impact but inverts here. The clause also carries the whole weight of decision `[8]`'s claim to put the obligation "where the caller reads it".
- Fix: Delete the clause from the round-trip scenario in `specs/_plans/add-filesystem-session-store/platform/session-store-port/spec.md`; the port delta's required scenario is supplied by the `DELTA:NEW` scenario in the preceding BLOCKER. Move the constraint into `adapters/filesystem-session-store/spec.md` as a `DELTA:NEW` scenario — `Scenario: State the store cannot serialise does not survive the round trip` — with a `TState` carrying a nested `Date`, asserting that `load` returns that field as an ISO string while the envelope's own two timestamps return as `Date`. Retarget `plan.md` task 5 and the § Verification coverage row accordingly.

#### [COMPLETENESS_GAP] BLOCKER
- Location: `adapters/filesystem-session-store/spec.md` § Scenarios (all nine); `plan.md` § Requirements → Atomic write, Write order
- Issue: `save` has no failure behaviour anywhere in the delta. Nine scenarios cover the happy path, `load`'s two policies, `list`'s skip policy, the identifier predicate and the environment resolver; not one describes what `save` does or leaves behind when it fails. Three concrete paths are unspecified and untested: (a) the write of `transcript.md` fails after `session.json` has already been renamed into place — the store is left half-committed and no scenario says whether `save` rejects, retries or cleans up; (b) `writeFile` succeeds and `rename` fails, leaving an orphan `<target>.<uuid>.tmp` in the session directory, which the `Saving replaces an earlier revision` scenario's "MUST hold exactly `session.json` and `transcript.md`" clause forbids on the happy path only; (c) `JSON.stringify` throws on a `TState` holding a `BigInt` or a cycle. Most seriously, the § Goals promise "a crash during `save` that cannot destroy the previous revision" — the plan's single most-argued design decision, defended across a § Patterns row, a § Consequences row, a § Requirements row and decision `[5]` — has no scenario and no row in § Verification § Scenario Coverage. Under speq's own evidence rule the plan would record a guarantee it never demonstrated.
- Fix: Add a `DELTA:NEW` scenario to `adapters/filesystem-session-store/spec.md` — `Scenario: A save that fails leaves the previous revision loadable` — asserting that when the write of either file fails, `save` MUST reject, the previously saved revision MUST still `load`, `list` MUST still report the identifier, and the session directory MUST hold no leftover temporary file. Add the matching row to `plan.md` § Verification § Scenario Coverage and a clause to task 2 naming the injection method (make the session directory read-only after the first successful save, or save a `TState` that `JSON.stringify` rejects). State in § Requirements which of the two files `save` writes first on failure and whether it removes its own temporary file.

#### [REQUIREMENT_CONFLICT] ADVISORY
- Location: `adapters/filesystem-session-store/spec.md` § Scenarios, `A damaged session file fails loudly`, final clause vs `plan.md` § Requirements → Envelope validation, Version check
- Issue: the scenario requires that "a `schemaVersion` the store does not recognise MUST reject the same way, with a message naming the version found and the version expected". § Requirements types `schemaVersion` as an integer inside the `zod` object and checks the value "outside the schema". A `session.json` carrying `"schemaVersion": "2"` or `"schemaVersion": 1.5` is a version the store does not recognise, but it fails the schema, so the rejection carries a `zod` field error and names neither the version found nor the version expected. The plan never fixes the order of the two checks, so the message a caller gets for a non-integer version is undetermined.
- Fix: In `plan.md` § Requirements § Version check, state that the version is read from the parsed JSON **before** the envelope schema runs, and that any value other than the number `1` — including a non-integer one — produces the version-mismatch rejection naming found and expected. Drop `schemaVersion` from the `zod` object, or note that its constraint is then redundant.

#### [COMPLETENESS_GAP] ADVISORY
- Location: `adapters/filesystem-session-store/spec.md` § Scenarios, `A session identifier never escapes the store's root` and `A damaged session file fails loudly`
- Issue: two cases fall through the merge. (a) § Requirements § Identifier safety and `decision-log.md` `[6]` both reject "a NUL byte", but the scenario's `WHEN` lists only "empty, is `.`, is `..`, or contains a path separator" — so the recorded spec never asserts the NUL case and task 2, which derives tests from scenarios, writes no test for it. (b) The damaged-file scenario's clause "its `cause` MUST carry the underlying failure **where one exists**" is an escape clause of the kind `/speq:writing-guardrails` bans, and it is the clause that makes the merge non-verifiable: of the four bundled bodies, bad JSON and a filesystem error have an underlying error while a version mismatch and an id mismatch do not, and the spec never says which is which. A test can satisfy the clause by asserting nothing.
- Fix: Add "contains a NUL byte" to the `WHEN` of `A session identifier never escapes the store's root` in `adapters/filesystem-session-store/spec.md`, or delete the NUL case from `plan.md` § Requirements § Identifier safety and `decision-log.md` `[6]`. Replace the "where one exists" clause with two explicit clauses: a rejection over a malformed body MUST carry the parsing or filesystem error as `cause`; a rejection over a version or identifier mismatch MUST carry no `cause` and MUST name both values.

#### [AMBIGUOUS_REQUIREMENT] ADVISORY
- Location: `adapters/filesystem-session-store/spec.md` § Scenarios, `A saved session carries a transcript beside its state`, final clause
- Issue: "a second save MUST rewrite the transcript, so it never describes an earlier revision" is not testable as written. § Requirements § Transcript body fixes the transcript's content as the identifier and both timestamps and nothing else, so two saves with the same `updatedAt` produce byte-identical files and the assertion passes whether or not the file was rewritten. The neighbouring `Saving replaces an earlier revision` scenario stipulates "a later `updatedAt`"; this one does not. The word "never" also overstates what the design delivers — `plan.md` § Consequences accepts that the transcript lags after an interrupted save.
- Fix: In `adapters/filesystem-session-store/spec.md`, change the `WHEN` of `A saved session carries a transcript beside its state` to save the same identifier twice with a later `updatedAt`, and change the final clause to "the transcript MUST name the second revision's `updatedAt`". Replace "never describes an earlier revision" with a clause scoped to a completed save.

#### [REQUIREMENT_CONFLICT] ADVISORY
- Location: `plan.md` § Requirements → Environment vs § Design → Key interfaces
- Issue: § Requirements says "Read from `process.env` directly" while § Key interfaces declares `sessionStoreConfigFromEnv(env?: NodeJS.ProcessEnv)` and every § Manual Testing row passes an environment in. The two sentences instruct different implementations. The plan also claims symmetry with `llmConfigFromEnv` but writes an asymmetric signature: the precedent at `packages/server/src/adapters/llm/openai-compatible-llm.ts:130` is `env: NodeJS.ProcessEnv = process.env`, a defaulted parameter, not an optional one the body must unwrap.
- Fix: In `plan.md` § Design → Key interfaces, change the signature to `env: NodeJS.ProcessEnv = process.env`, matching the precedent. In § Requirements § Environment, replace "Read from `process.env` directly" with "The parameter defaults to `process.env`; the resolver reads no file."

## Design Depth

No objection on the module's shape — axis checked against the Quick Diagnostic: `createFilesystemSessionStore` is deep (callers learn three domain methods and never the directory layout, the envelope, `schemaVersion`, the temporary-file dance or the classification rules); one sentence captures its responsibility; `packages/core` keeps its dependency direction, verified against `tests/workspace.test.ts:297`, which inspects only `packages/core`'s manifest and the import specifiers of its non-test files — so the plan's claim that `platform/core-ports-contract` needs no delta holds, and its Background sentence is scoped to the package rather than the port. The transcript stub is a tactical shortcut with a named follow-up (M3/M15). The identifier predicate closes traversal completely: `..`, `.`, empty, `/`, `\` covers `/etc/passwd`, `a/../../b` and `..\..\x` alike. `rootDir` as a parameter rather than a constant is the right call under the configuration-parameter test, because it is the same seam production needs.

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: `decision-log.md` `[8]`; `plan.md` task 5; `platform/session-store-port/spec.md`
- Issue: the plan opens with "One module in `packages/server` owns the fact that a session is a folder on disk. Nothing else in the workspace learns it", then routes one specific decision of that module — JSON as the serialisation format — out through the port spec and into `packages/core`'s own test file, as a double built on `JSON.parse(JSON.stringify(...))` plus a hand-written revival of the two timestamps. `packages/core` now encodes both the format choice and the envelope's timestamps-are-special rule. Change the adapter's format to one that carries `Date` natively and the port scenario, the core test double and the adapter all need editing together — the recurrence the design philosophy treats as the defect deserving closest attention. The plan does not acknowledge the leak; it presents the edit as putting a constraint "where the caller reads it".
- Fix: Add a row to `plan.md` § Consequences naming the leak and the reason it is accepted — that every planned store, including P1's hosted one, serialises — or express the port-level requirement without naming a format, as "a store that outlives a process returns only what its format preserved" with the double parameterised over a serialise/revive pair rather than hard-coding `JSON`.

# Plan Review Findings: change-language-switch-restarts-interview (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 10 (Blockers: 3, Advisory: 7)
- Intent Fidelity blockers: 0

All three blockers share one root: `pending` — the flag that decides whether the discard
request is on screen — is the only piece of round state with no owner. It is set in two
places, cleared in two others, and named in neither the effect-body reset nor
§ Requirements' "A restart resets the round completely" row.

## Intent Fidelity

#### [SCOPE_REDUCTION] ADVISORY
- Location: plan.md § Key interfaces (`OPEN_PHASES`), § Consequences row "`submitting` counts as closed"; decision-log.md [6]
- Issue: the clarifying interview exempted the state where the answer "has already been submitted **and confirmed** (`recorded` state)". The plan widens that exemption to `submitting` — "A round is open while it can still be restarted — that is, until the answer is on the wire". In `submitting` the question is still unanswered by the user's framing, and the exemption is not one the user granted. The rationale is sound and recorded, but it is the planner's call, not the interview's, and it is the call that makes a refused submission reachable with `pending` still set (see BLOCKER in § Requirement Quality).
- Fix: Add one line to plan.md § Non-Goals stating that `submitting` is exempted by this plan rather than by the clarifying interview, and name the window it covers (one in-flight `submitAnswer` call). Add the same note to decision-log.md [6] under **Decision**, so the human approving the plan sees it as a planner decision.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: plan.md § Architecture (the request block, line 71), § Decision "The restart is the effect re-running" (the reset snippet), § Requirements row "A restart resets the round completely"; spec delta § Scenario "Confirming the discard restarts the interview in the chosen language"
- Issue: confirming the discard leaves the request on screen. The plan defines `discard → beginRound(locale); focus the interview region` and `beginRound(next) = setRound({ index: round.index + 1, locale: next })` — neither clears `pending`. The effect-body reset lists exactly six values plus `submitting.current`; `pending` is not among them. The render condition is "rendered while `pending` && round open", and `beginRound` drives the phase to `connecting`, which `OPEN_PHASES` declares open. So after a confirmed discard `pending` is still `true` and the phase is still open: the request re-renders over the fresh round. That contradicts the delta's own `AND` — "the first question's text, the typed text and **the request itself MUST all be gone**" — and § Requirements' claim that a restart returns the round to its mount values. The plan asserts the outcome and specifies a mechanism that cannot produce it.
- Fix: In plan.md § Architecture, change the request block's discard line to `discard → setPending(false); beginRound(locale); focus the interview region`, and add `setPending(false);` to the § Decision effect-body snippet, restating "the round's six state values" as seven in § Requirements' "A restart resets the round completely" row and in § Migration. Add an explicit assertion to the task 2 test named in § Scenario Coverage row 2 — that the discard request is absent after the confirmed restart — and name it in the test title.

#### [HIDDEN_DEPENDENCY] ADVISORY

## Requirement Quality

#### [COMPLETENESS_GAP] BLOCKER
- Location: plan.md § Decision ("Render the request only while `pending` and the phase is open, which is what makes recording the answer withdraw it without a second code path"), § Consequences row "`submitting` counts as closed"; spec delta § Scenario "Switching the chrome's language asks before discarding a typed answer"
- Issue: a refused submission resurrects a stale request. The path is reachable and already specified: the person types an answer, switches the language (request opens, `pending` true), then records the answer instead. Phase goes `submitting` — the request hides, `pending` stays `true` — and `api.submitAnswer` answers `{ outcome: 'refused' }`, which `InterviewView.tsx:118-122` turns into phase `failed`. `failed` is in `OPEN_PHASES`, so the request returns to the screen, asking whether to discard an answer the person already sent and whose text `failed` no longer renders. The plan reads this transition as a virtue — "A refusal returns the phase to `failed`, which is open again, so nothing is stranded" — without noticing that `pending` survives it. No requirement, scenario or task covers the state. The same hole covers a second reachable case the delta leaves open: scenario 1 requires "the answer field and the submit control MUST stay usable" while the request is on screen, so the person can delete the draft, leaving a request that offers to discard nothing.
- Fix: In plan.md § Requirements, add a row stating that the discard request leaves the screen when the answer is sent and does not return, whatever the submission answers, and a row stating that emptying the answer field withdraws the request. Add a matching `AND` to the delta's scenario "Switching the chrome's language asks before discarding a typed answer" covering a refused submission, and add the clearing rule to plan.md § Architecture (clear `pending` when the phase leaves `OPEN_PHASES`, and when the draft becomes blank). Add both cases to task 2's test list in § Scenario Coverage.

#### [COMPLETENESS_GAP] BLOCKER
- Location: plan.md § Decision ("`failed` is open, not closed — the answer form is already gone in that state, so a restart discards nothing visible"), § Key interfaces (`OPEN_PHASES` doc comment), § Consequences row "`failed` counts as open", § Implementation Tasks task 2; spec delta § Scenario "Switching the chrome's language with nothing typed restarts the interview without asking"
- Issue: the plan's rule for `failed` contradicts its own gate. The gate branches on the `answer` state — "draft blank → `beginRound(locale)`", "draft non-blank → `setPending(true)`" — but the plan justifies `failed` being open with "the answer form is already gone, so a restart discards nothing the person can see". Both cannot hold: `InterviewView.tsx:131-132` excludes `failed` from `showAnswerForm`, yet `answer` is untouched by the failure path, so `failed` is reachable with `answer` non-blank via the refused-submission path the recorded spec already pins ("*AND* the view MUST show the same treatment when the answer route refuses the submission"). In that state the gate opens a request whose prompt names an answer the person cannot see, whose § Design Direction placement — "directly below the answer form", reading order "question → the draft at risk → the request" — has no answer form to sit below, and which shares the screen with the failure block's own `role="alert"`. Task 2 meanwhile prescribes "an `it.each` over `connecting`, `streaming`, `complete` and `failed`" asserting restart *without* asking, and the delta's `GIVEN` — "a view whose answer field holds no text" — is unsatisfiable in `connecting` and `failed`, where no answer field exists. The implementer has two incompatible rules and no tiebreaker.
- Fix: Pick one rule and state it once. In plan.md § Decision, replace the `failed` paragraph with the chosen rule — either the gate reads the draft only while the answer form is rendered (so `failed` and `connecting` always restart silently), or `failed` with non-blank `answer` asks and the request renders without an answer form. Update the `OPEN_PHASES` doc comment in § Key interfaces, the § Consequences "`failed` counts as open" row, and § Requirements' "A restart never discards typed text without consent" row to match. Restate the delta's fourth scenario `GIVEN` in terms of the state rather than the field ("a view holding no typed answer"), and add the `failed`-after-refusal case to task 2's test list in § Scenario Coverage.

## Task Breakdown

#### [TRACEABILITY_GAP] ADVISORY
- Location: plan.md § Scenario Coverage ("Task 2 deletes exactly one test and edits no other, in `InterviewView.test.tsx` alone; that `App.test.tsx` ... stay green without an edit is the evidence that the restart changed no behaviour outside the view")
- Issue: the nominated evidence does not support the claim. Four existing call sites now silently drive a full restart and none asserts it. `packages/web/src/App.test.tsx:161-166`, `:193-195` and `:221-226` each fire a language change against a ready gate with the view mounted, which under the new gate issues a second `createSession` plus a second `openQuestionStream`; those tests assert only the combobox and storage, so they stay green while the behaviour under them changed. `packages/web/src/InterviewView.test.tsx:276-281` — the test for the recorded scenario "The question is marked with the language it was asked in" — rerenders `locale="en"` to `locale="de"` with a blank draft in phase `complete`, which is now a restart; it still passes only because its `createSession` double returns `{ locale: 'de' }` regardless of the argument, so its closing assertion `getAttribute('lang') === 'de'` is satisfied by the second session rather than by the first. Green there proves the opposite of what the plan reads into it. The three `App.test.tsx` sites also leave a `createSession` promise resolving outside `act()`, which will emit React act warnings (not failures — `packages/web/vitest.config.ts` declares no setup file that escalates `console.error`).
- Fix: In plan.md § Scenario Coverage, replace the "stay green without an edit is the evidence" sentence with the four call sites named above and what each now exercises. State for `InterviewView.test.tsx:276-281` that the rerender step now triggers a restart and that task 2 MUST either stop the rerender from restarting (assert the question region's `lang` before the switch only) or assert the restart explicitly. Add a § Verification line naming the expected act-warning noise in `App.test.tsx` so the implementer does not read it as a regression.

#### [TASK_GRANULARITY] ADVISORY
- Location: plan.md § Implementation Tasks task 1 ("Extend `packages/web/src/locale/strings.test.ts` so each new member is present, non-blank, and different between the two languages, in the style the file already uses for the existing members")
- Issue: task 1 is not a red-green pair as written. `packages/web/src/locale/strings.test.ts:16-18` derives `STRING_MEMBERS` from `Object.keys(en)`, and the three generic tests at `:26`, `:33` and `:50` already assert presence, non-blankness and cross-language difference for every string member. Adding the four members to `en.ts` and `de.ts` extends that coverage with no test edit at all; a hand-written per-member assertion would duplicate it, which `/speq:code-guardrails` treats as test bloat. - Fix: Rewrite task 1 in plan.md § Implementation Tasks: state that the red step is `pnpm typecheck` failing once the four members are added to `UiStrings` and before both dictionaries carry them, that `strings.test.ts` needs no edit because its generic loops pick the members up from `Object.keys(en)`, and that no per-member assertion is to be added.

## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: plan.md § Decision "The effect owns what a round begins as", § Key interfaces (`Round`, `chosen`, `pending`); decision-log.md [5]
- Issue: the plan claims one owner for the round's state — "Putting the reset here makes the effect the single place that knows what a round consists of" — but a round is actually described by four things in three places: the `Round` value, six `useState`s reset inside the effect, the `submitting` ref, and `pending`, which belongs to the round's lifecycle and appears in none of the three. That is the recurring-decision leakage the plan's own rationale invokes, one level up: a later milestone adding a per-round flag will face the same three-way choice, and both blockers above are the first instance of it. The `chosen` value compounds it by encoding "which chrome language has this round already answered for" separately from the round it answers for.
- Fix: In plan.md § Key interfaces, fold the request into the round value — for example `Round { index, locale, request: 'none' | 'pending' }` — so one value names which round is running and whether its restart awaits consent, and the effect's reset covers it by construction. Record the change in decision-log.md as a revision of [4] and [5], naming the alternative kept (three separate values) and why it was dropped.

## Premortem

Three ways this plan fails in six months, each routed into the taxonomy below.

1. **M6 is marked ✅ and the setup screen is still task 9's unstyled markup.** The impeccable subphase never ran, task 13 was archived with the plan, and nothing outside the archive remembered it was owed. → Intent Fidelity, `[SCOPE_REDUCTION]`.
2. **The deadline was never exercised.** The fake-timer advance in task 3 is inert against `AbortSignal.timeout`, so the case passed on 2 s of real wall-clock time while asserting nothing about the bound. A person with a mis-set `CHRYSALYST_LLM_BASE_URL` sits on `Checking the language model…` forever — the hang the plan names as a Goal. → Feasibility, `[UNSTATED_ASSUMPTION]`.
3. **A person presses "Check again" against a stopped daemon.** Nothing visibly changes for 2.0 s, so they press it four more times; five probes race with no ordering rule and the screen flickers between guidance and checking. They conclude the app is broken — the exact outcome M6 exists to remove. → Requirement Quality, `[COMPLETENESS_GAP]`.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: `plan.md` § Implementation Tasks task 3 and task 4; `plan.md` § Consequences (the 2.0 s deadline row); `decision-log.md` `[4]`; `platform/backend-status/spec.md` § Scenario: A probe that does not answer in time reports the backend unreachable
- Issue: task 3 specifies the deadline's only test as »a double whose `status` settles only when its signal aborts, with **Vitest's fake timers advanced past `BACKEND_PROBE_DEADLINE_MS`**«, and task 4 mandates the implementation »probes with `AbortSignal.timeout(BACKEND_PROBE_DEADLINE_MS)`«. Those two are jointly infeasible. `AbortSignal.timeout` is a native Node binding that holds its own timer reference; it does not route through `globalThis.setTimeout`, which is the only thing `vi.useFakeTimers()` replaces. Verified empirically on this repository's runtime (Node v22.23.2):

  ```
  globalThis.setTimeout intercepted calls: 0
  AbortSignal.timeout fired despite faked global setTimeout: true
  ```

  (A script replacing `globalThis.setTimeout`/`clearTimeout` with no-ops, then waiting 300 ms of real time on an `AbortSignal.timeout(80)`: the global was never called, and the signal aborted anyway.)

  So `vi.advanceTimersByTime(BACKEND_PROBE_DEADLINE_MS + 1)` cannot fire that signal. The double never settles from the advance. The case then either (a) silently waits 2 s of real wall-clock time and passes while proving nothing about the advance — inside Vitest's 5000 ms default `testTimeout`, leaving 3 s of margin on the suite's slowest case — or (b), if written as advance-then-assert, never settles and fails. Either way the plan's flagship § Requirements row »**Nothing hangs** — The probe is abandoned after 2.0 s« has no test that actually observes the bound, and a later change that drops the abort entirely would not go red.

  § Consequences closes the escape hatch by rejecting »a configurable deadline«, so the test cannot shrink `BACKEND_PROBE_DEADLINE_MS` either. This is the one piece the plan itself calls »the one piece of non-obvious correctness in this plan« (§ Parallelization, task 4 `[expert]`).
- Fix: In `plan.md` task 4 and § Key interfaces, replace `AbortSignal.timeout(BACKEND_PROBE_DEADLINE_MS)` with a signal built from `new AbortController()` plus a `setTimeout(…, BACKEND_PROBE_DEADLINE_MS)` that `readBackendReadiness` clears on every settle path — `setTimeout` is a global Vitest fake timers do replace, so task 3's stated mechanism then works unchanged and the adapter's `cancelled(signal)` rethrow path is unaffected. Add to task 4 the explicit requirement that the timer is cleared when the probe answers before the deadline, so no test leaves a pending handle. Update `plan.md` § Dependencies, which currently rests the design on »`AbortSignal.timeout` is Node 22 and browser standard and needs no polyfill«. Add to task 3 a sentence stating why the deadline is not built with `AbortSignal.timeout` — that it is unreachable from fake timers — so a later refactor does not silently reintroduce the untestable form.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: `plan.md` § Goals (»no page waits longer than 2.0 s«); § Requirements (»Nothing hangs«); § Consequences (the deadline row, »lets the browser inherit it«); `decision-log.md` `[4]` (»The browser sets no timeout of its own«)
- Issue: the bound is a property of the route, restated in § Requirements as a property of the app. The browser's `fetch` to `/status` carries no deadline, so the claim »the browser inherits the bound by asking a route that is already bounded« holds only while the API server answers. A stopped API server fails fast with `ECONNREFUSED` and reaches the failure screen — § Manual Testing covers that. A **hung** API server does not: the shell sits on `setupChecking` indefinitely, and that state renders no control (the check control lives on `SetupGuide`, not on the checking state), so the person has no action and no message. `platform/backend-setup-gate`'s § Scenario: Nothing is mounted while the probe is in flight asserts the checking state and bounds nothing.
- Fix: Pick one and make `plan.md` say it. Either narrow the § Requirements »Nothing hangs« row and the § Goals bullet to name the route (»the route answers within 2.0 s of a backend that never answers; the browser leg is unbounded and a hung API server is out of scope for M6«), and add that limitation to `decision-log.md` `[4]` § Alternatives as an accepted cost — or bound the browser leg too: add a deadline to `fetchBackendReadiness` in § Key interfaces, a scenario to `platform/backend-setup-gate` covering a probe that never answers reaching the failure screen, and the corresponding assertion to task 7.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: `plan.md` § Decision (»Ollama's `/v1/models` answers the ids `ollama list` shows, tag included«); `decision-log.md` `[3]`; task 12
- Issue: the whole `model-missing` fault rests on that sentence, and the plan cites no source for it — no Context7 lookup, no captured payload, no test at plan time. If Ollama's OpenAI-compat layer reports an id in any other form, exact equality reports `model-missing` on a machine that would in fact answer, and the gate blocks a working backend: the worst failure this milestone can produce. The plan names task 12 as the guard, but task 12 is weaker than claimed on two counts. It runs only under `CHRYSALYST_LIVE_LLM=1`, an opt-in tier absent from CI. And it asserts only the **happy** direction — a daemon holding `qwen3:8b` against a descriptor naming `qwen3:8b`. The near-miss the rule actually turns on, `llama3.2:latest` not satisfying `llama3.2:3b`, is exercised only against a stub in task 3's `it.each`; no real `/v1/models` payload ever falsifies it. § Manual Testing's `model-missing` row uses `not-a-real-model`, which proves nothing about tag form.
- Fix: Add to `plan.md` task 12 a second live assertion: with the daemon running, dispatch `GET /status` against a descriptor whose model is the configured id with its tag replaced by `:latest` (or stripped entirely), and assert `reason` is `model-missing` — so the exact-match rule is falsified against a real payload in both directions. Add a `plan.md` § Dependencies line naming the Ollama `/v1/models` response shape the design assumes, with the source it was checked against.

## Requirement Quality

#### [COMPLETENESS_GAP] BLOCKER
- Location: `platform/backend-setup-gate/spec.md` § Scenario: Checking again after the backend is fixed opens the interview; `plan.md` § Implementation Tasks task 10
- Issue: the re-check is specified only at its endpoints. The scenario says »the shell MUST run the probe again« and »MUST mount the interview view once the second answer arrives«, and says nothing about the window between the activation and the answer. That window is up to the full 2.0 s the plan itself introduced, and against a stopped daemon it is the common case. Two behaviours both satisfy the scenario as written:
  - the screen shows nothing new for 2.0 s — the person presses the control repeatedly, which is precisely the »app feels broken« outcome M6 exists to remove; or
  - the screen returns to the checking state, and the control the person just pressed disappears under their cursor.

  Neither is chosen, and § Design Direction's open question — »whether the checking state is a line of text or occupies the screen the guidance will fill, so the swap does not jump« — is about visual jump, not about which state is entered.

  The same gap leaves **concurrency unspecified**. Nothing says the control is disabled while a probe is in flight, and nothing states an ordering rule for overlapping probes. Task 10 requires only that a probe resolving after *unmount* is abandoned; a probe superseded *within* a mount is not mentioned, so a slow first answer landing after a fast second one may overwrite it and show a stale fault on a backend that is now ready. Task 10 is `[expert]` precisely because »an effect whose dependency list decides whether a language switch quietly orphans a session« — the same effect, with the same unspecified races, carries the re-check.
- Fix: Add to `platform/backend-setup-gate/spec.md` a `DELTA:NEW` scenario — `Re-checking shows that it is checking and answers once` — asserting that activating the control puts the shell into the same labelled checking state the first probe uses, that the setup screen's fault text is not shown while that probe is in flight, that activating the control while a probe is unsettled does not start a second probe (or that only the newest probe's answer is rendered — pick one and state it), and that an answer from a superseded probe MUST NOT replace a newer one. Add the matching test name to `plan.md` § Verification § Scenario Coverage against `app.test.tsx` (task 10), and add to task 10 the sentence naming the supersede rule the effect's cleanup must implement.

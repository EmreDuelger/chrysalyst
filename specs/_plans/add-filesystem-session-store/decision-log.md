# Decision Log: add-filesystem-session-store

## Interview

**Q:** M2 promises a Markdown transcript per session, but there is no interview state yet, `TState` arrives in M7, and no transcript renderer exists. What does the transcript hold in M2?
**A:** Write it now as a metadata stub. `save()` always writes a minimal `transcript.md` with a header carrying `id`, `createdAt`, and `updatedAt`, and nothing else. M3 and M15 replace it with real rendering once there is interview content and a core-side renderer. Decide during planning whether the roadmap wording needs a one-line correction, following the precedent where `002-add-ollama-llm-adapter` corrected roadmap § M1.

**Q:** `load(id)` finds a folder whose `session.json` is present but unreadable — a JSON parse error, or an unrecognised `schemaVersion`. What happens?
**A:** Throw a descriptive error naming the path and the cause. A present-but-broken file is data corruption, categorically different from "not there". `undefined` stays the outcome for genuinely missing identifiers only. This applies to both parse errors and an unknown or unexpected `schemaVersion`; the forward-compatible option, where an unknown version resolves to `undefined`, is explicitly rejected.

**Q:** Where does the adapter get its root directory? Tests need a `mkdtemp` path; production wants `~/.chrysalyst/sessions`.
**A:** A config argument plus an environment helper, mirroring the LLM adapter. `createFilesystemSessionStore({ rootDir })` takes `rootDir` explicitly. A separate helper resolves `CHRYSALYST_SESSION_DIR` with the default `~/.chrysalyst/sessions`, named symmetrically with `llmConfigFromEnv` from plan 002. That helper is the single composition seam where the default is written down once.

**Q:** `list()` finds a subdirectory in the root with no `session.json`, or a broken one — a half-written folder, a manually created directory, a `.DS_Store`. What happens?
**A:** Skip silently. `list` returns only identifiers that have a readable `session.json`. That is consistent with the port's own comment that a stale link is an ordinary outcome rather than a failure, and with the spec promise that `list` finds exactly the written identifiers. The asymmetry with the previous answer is deliberate — `list` skips an unreadable entry while `load` of a specific identifier rejects — and the plan must state it explicitly so the reviewer does not read it as an inconsistency.

## Design Decisions

### [1] Absence and corruption are different answers, and the two readers disagree on purpose

- **Decision:** One private reader classifies a session folder as absent (`ENOENT` on `session.json` or on its directory) or unreadable (every other filesystem error, a `JSON.parse` failure, an envelope-schema failure, a `schemaVersion` the store does not recognise, and a stored `id` that disagrees with its directory name). `load` resolves `undefined` for absent and rejects for unreadable, with a message naming the file's absolute path. A rejection over a malformed body — bad JSON, a schema failure, a filesystem error — carries that error as `cause`; a rejection over a version mismatch or an `id` mismatch has no underlying error to carry, so it carries none and names both values instead. `list` drops both classes and returns what remains.
- **Alternatives:** Resolving `undefined` for both classes — rejected because M3's walking skeleton would then silently start a fresh interview over a session whose file it failed to read, and the user would lose work without a message. Resolving `undefined` for an unrecognised `schemaVersion` while rejecting a parse error, so a future format degrades to "not found" — offered in the interview and explicitly rejected: a version the store cannot read is a file it cannot read. Failing the whole `list` over one damaged folder — rejected because a session library that will not open until a stray directory is deleted is worse than one that shows what it can read.
- **Rationale:** Two callers ask different questions of the same bytes. `load` names one session, so it owes an answer about that session and must not disguise corruption as absence. `list` asks what the store holds, and one damaged folder is not an answer to that question. Putting the split in the two public methods rather than in two readers keeps exactly one owner of the file format, so the classification cannot drift between them. `list` reuses the full read rather than a cheaper "does the file parse" check, which is what makes its promise honest: every identifier it reports is one `load` will answer.
- **Promotes to ADR:** yes

### [2] `schemaVersion` versions the envelope on disk, not the session in the domain

- **Decision:** `session.json` is an envelope — `{ schemaVersion, id, createdAt, updatedAt, state }` — whose `schemaVersion` is the number `1`, held as a constant in the adapter module. `StoredSession` in `@chrysalyst/core` gains no such field. The store validates the envelope with `zod` and passes `state` through untouched, reaching `TState` by a single documented type assertion.
- **Alternatives:** Adding `schemaVersion` to `StoredSession` — rejected because `platform/core-ports-contract` forbids the filesystem in `core`, and because a hosted store (roadmap P1) writes no `session.json` and would carry a field that means nothing to it. A version string such as `"1.0"`, or the package version — rejected because an integer that increments when the envelope's shape changes is the smallest thing a future reader can branch on, while a package version bumps on releases that change no format. Accepting a `parseState` validator in the config so the store could check `TState` too — rejected as a decision the module would be declining to make for a caller that does not exist; no feature before M9 has a state schema to hand it.
- **Rationale:** The roadmap makes `schemaVersion` a standing guardrail from the first write, because `TState` grows across M2 → M8 → M9 → M14 and an unversioned folder breaks silently later. Versioning the envelope rather than the state is what lets that growth happen without touching this module: the envelope's shape is the adapter's business and the state's shape is the caller's. The price is stated rather than hidden — `TState` must survive a JSON round trip, so a `Date` nested inside the state returns as a string, and only the two timestamps the envelope owns are revived. M3 picks the concrete `TState` and inherits that constraint.
- **Promotes to ADR:** yes

### [3] The store root is a constructor parameter, and one helper owns its default

- **Decision:** `createFilesystemSessionStore({ rootDir })` takes the root explicitly. `sessionStoreConfigFromEnv(env: NodeJS.ProcessEnv = process.env)` resolves `CHRYSALYST_SESSION_DIR` — absent or empty gives `join(homedir(), '.chrysalyst', 'sessions')`, a set value is resolved to an absolute path — and is the only place that default is written down. The resolver reads no file.
- **Alternatives:** A module constant pointing at the home directory, with tests monkey-patching `homedir` or `process.env` — rejected because a test that mispatches writes into the user's real sessions, and because the same seam that makes a test hermetic is the one production needs anyway. Expanding a literal `~` inside a `CHRYSALYST_SESSION_DIR` value — rejected as a mini-shell: shells expand `~` themselves, so a value arriving with a literal tilde was quoted deliberately. Leaving a relative value relative — rejected because the store's root would then move with the working directory.
- **Rationale:** This mirrors `llmConfigFromEnv` from plan 002 down to its signature — a defaulted `env` parameter, not an optional one the body must unwrap — so both adapters in `packages/server` are configured the same way and a reader learns the pattern once. Passing the environment in rather than reading ambient state keeps the resolution a pure function of its input. `os.homedir()` and `process.cwd()` are ambient state but not file reads, so the no-dotenv-loader promise holds precisely.
- **Promotes to ADR:** no

### [4] The transcript ships in M2 as a metadata stub, and the roadmap's completion criterion is corrected to say so

- **Decision:** `save` writes `<root>/<id>/transcript.md` containing a Markdown header that names the identifier and both timestamps, and nothing else. The spec asserts those invariants rather than the exact bytes, so M3 replaces a body without a spec fight. Task 14 extends roadmap § M2's `**Fertig, wenn:**` clause to name the transcript stub.
- **Alternatives:** Deferring the file to M3, when there is content to render — rejected because roadmap § M2's `**Liefert:**` promises a Markdown transcript per session, and a milestone should not be recorded as met while one of its deliverables is absent. Rendering something richer now — rejected because there is no interview content to render and no renderer; anything richer would be invented data.
- **Rationale:** Writing the file now fixes its name and location while nothing depends on its body, so M3 changes a body rather than introducing a file into a layout other code has begun to assume. The roadmap correction is the honest half of the trade: `**Fertig, wenn:**` currently checks only `session.json`, so a reader cannot tell the transcript is in M2's scope, and `/speq:audit` would read the milestone's criterion as narrower than what ships. `session.json` is renamed into place before `transcript.md` is, because a derived view that lags is ordinary while one describing a revision the store never committed is a lie.
- **Promotes to ADR:** no

### [5] A failed `save` must leave the previous revision loadable, so both files are staged then renamed

- **Decision:** `save` serialises the envelope, writes each file to `<target>.<randomUUID()>.tmp` in the target's own directory, syncs it (decision `[10]`), and only then renames both onto their targets — `session.json` first. A failure at any step removes the temporary files `save` created and rethrows the original error. Concurrent saves of one identifier are last-writer-wins; no lock and no compare-and-swap.
- **Alternatives:** A plain `writeFile` — rejected because it interacts badly with decision [1]: a crash mid-write leaves a truncated `session.json`, which then rejects on every subsequent `load`, so one interrupted write would destroy a session permanently rather than costing it one revision. Renaming each file as soon as it is written — rejected because a transcript write that fails after `session.json` is committed leaves the store half-committed, and `save` could then promise nothing about what a caller loads next. A lockfile or a compare-and-swap parameter on `save` — rejected because `SessionStorePort` declares no such parameter, so a store has nobody to report a conflict to.
- **Rationale:** `rename` within one directory replaces the target in one step — verified against this Node build — so no reader ever observes a torn file; decision `[10]` adds the barrier that extends that from a process crash to a power loss. Staging narrows the window in which a failure can be observed rather than closing it: every failure at or before the `session.json` rename now commits nothing, leaving the previous revision whole, and only the gap between the two renames remains. That residual gap leaves the new `session.json` beside the previous `transcript.md`, which is the lagging derived view decision `[4]` already accepts, and the rename order is chosen so the residue falls on that side rather than the reverse. Undoing it would need a backup copy of the previous `session.json` and a rollback that can itself fail — § Consequences records that trade. Staging also gives the failure path exactly one thing to undo, so the cleanup is a `rm(tmp, { force: true })` per staged file and cannot mask the rejection that named the fault. The UUID in the temporary name keeps two concurrent saves of one identifier off the same path.
- **Promotes to ADR:** no

### [6] An identifier is a single path segment, and all three methods agree on which ones exist

- **Decision:** One predicate rejects an identifier that is empty, is `.`, is `..`, or contains `/`, `\`, or a NUL byte. `save` rejects such an identifier with an error naming it, before touching the filesystem. `load` resolves `undefined` for one, reading nothing. `list` filters directory names through the same predicate.
- **Alternatives:** Trusting the caller, since identifiers are generated by chrysalyst — rejected because `SessionId` is a bare `string`, so nothing in the type system stops a future HTTP route from passing a path through. Rejecting characters that are merely illegal on Windows as well — rejected because one rule that answers the same way on every platform beats a rule that accepts an identifier on Linux and refuses it on Windows; M3 picks the identifier format and should pick from the safe set. Rejecting from `load` too — rejected because an identifier the store refuses to write is one it never stored, so "not there" is literally true, and it keeps `load`'s promise never to throw over an absent session.
- **Rationale:** `<root>/<id>` must stay inside `<root>`, and the predicate is what guarantees it. Applying it in `list` as well is what keeps the three methods consistent: a directory whose name contains a backslash is creatable on Linux, and without the filter `list` would report an identifier that `load` answers with `undefined`.
- **Promotes to ADR:** no

### [7] `zod` validates the envelope, and the version is checked before it runs

- **Decision:** The version is read from the parsed JSON and compared to the number `1` **before** the envelope object runs. The object itself covers only what the version check does not own — `id` a non-empty string, both timestamps `z.iso.datetime()`, `state` `z.unknown()` — and carries no `schemaVersion` field at all.
- **Alternatives:** A hand-written type guard, as `isModelList` already is in the LLM adapter — rejected on two counts: `zod` reports which field failed, which is what the rejection message has to name, and `z.iso.datetime()` closes the hole a hand-written guard usually leaves open, where `new Date('garbage')` yields an `Invalid Date` silently instead of throwing. `z.literal(1)` for the version — rejected because its failure message names neither the version found nor the version expected, which is exactly what the interview asked the error to say. Typing `schemaVersion` as an integer inside the object and checking the value after it — rejected because it splits one fault across two messages: `"2"` and `1.5` are versions the store does not recognise, but they fail the object first and produce a `zod` field error naming neither value, so the caller's message depends on which kind of wrong version it met.
- **Rationale:** Checking the version first is what makes its message reachable for every wrong version rather than only for a wrong integer, and it puts one owner on one fault. `zod` is already declared in `packages/server`, so this adds nothing to the dependency tree. Two behaviours were verified against the installed `zod@4.5.4` rather than assumed: `z.unknown()` rejects an absent key rather than treating it as optional, so a truncated envelope fails instead of loading as `state: undefined`; and `z.iso.datetime()` accepts `Date.prototype.toISOString()` output exactly. The first has a consequence worth stating — `TState` must serialise to a defined JSON value — and it is recorded in § Requirements rather than discovered during implementation.
- **Promotes to ADR:** no

### [8] The port records that `load` can reject; the adapter records what serialisation costs

- **Decision:** `platform/session-store-port` gets a delta on two fronts. Its Background drops the claim that the port has no adapter. Its § Scenarios gains one scenario, `A stored session the implementation cannot read is a failure`, binding every implementation: `load` rejects over a record that is present but unreadable, `undefined` reports absence alone, and `list` does not reject over a record it cannot read. Task 13 proves it with a third double in `packages/core/src/ports/ports.test.ts` and amends the `load` doc comment in `packages/core/src/ports/session-store.ts`. The serialisation constraint is recorded one level down, in `adapters/filesystem-session-store`'s `State the store cannot serialise does not survive the round trip`.
- **Alternatives:** A Background-only delta, leaving the scenarios untouched — rejected because `load`'s new rejection path is a contract change that every caller and every future implementation reads at the port, not in one adapter's spec. Stating the rejection path only in the adapter's spec — rejected because P1's hosted store faces the same question and nothing would tell it the answer. Recording the serialisation constraint at the port instead — rejected because a port-level double can only demonstrate it by hard-coding `JSON` into `packages/core`, which leaks the adapter's format choice upward; the loss is observable where it happens, against real files. Making `memorySessionStore` itself serialise — rejected because it would break the existing `Date` equality assertion the round-trip scenario already owns.
- **Rationale:** The two facts sit at different levels. That `load` can reject is a promise every implementation must keep and every caller must handle, so it belongs where callers read the contract; leaving it in one adapter's spec would let M3 call `load` on the port's documented promise that a stale link "is an ordinary outcome, not a failure" and meet an unhandled rejection. That a `Date` inside `TState` returns as a string is a consequence of one format choice, provable only by an implementation that has one — asserted at the port it is either vacuous over a JSON-safe fixture or a statement about `JSON` that `packages/core` has no business making. Both edits stay inside `packages/core`'s purity rule: `tests/workspace.test.ts` reads the manifest and the import specifiers of non-test files, and neither a test double nor a doc comment touches either.
- **Promotes to ADR:** no

### [9] No `delete`, and no `platform/core-ports-contract` delta

- **Decision:** No `delete` method reaches the adapter or the port. `platform/core-ports-contract` gets no spec delta.
- **Alternatives:** Adding `delete` now, while the adapter is open — rejected: `decision-log [9]` of `001-add-monorepo-scaffold` defers it until a feature needs it, and roadmap § M17 owns the delta that adds it. Writing a `core-ports-contract` delta defensively — rejected after checking the wording: its "Core carries no runtime dependency" scenario asserts facts about `packages/core`'s manifest and its non-test source, which this plan does not touch, and its Background sentence is scoped to the package rather than to the port, so it stays true while an adapter lands in `packages/server`.
- **Rationale:** An unasked method is one every future adapter implements untested, which is the reasoning already recorded in the port's own doc comment. The `session-store-port` Background is the one sentence this plan falsifies outside a scenario, and § Impact flags it rather than leaving it to the merge, because `/speq:spec-merge` maps `DELTA:CHANGED` to scenarios only and would otherwise skip a Background block silently — the finding `002-add-ollama-llm-adapter` recorded for `llm-port`.
- **Promotes to ADR:** no

### [10] Each temporary file is `fsync`ed before its rename; the session directory is not

- **Decision:** `save` writes each temporary file through `open(tmp, 'w', 0o600)`, `handle.writeFile(...)`, `handle.sync()`, then renames it onto its target. It issues no `fsync` on the session directory or on the root after the renames.
- **Alternatives:** No barrier at all, relying on `rename` alone — rejected because `rename` orders nothing against the data blocks: after a power loss the directory entry can be on disk while the file body is not, leaving a truncated or zero-length `session.json` under the committed name, which decision `[1]` then rejects on every later `load`. That is precisely the permanent loss decision `[5]` set out to remove, so a mechanism that stops at a process crash would leave the § Goals promise half-kept. Also `fsync`ing the session directory after each rename, so the rename itself is durable — rejected on two counts: the residue it prevents is benign, because a lost rename leaves the previous revision whole, which is the same outcome as a save that never ran; and reaching it needs `open(dir)`, which POSIX permits and Windows refuses, so the store would carry a platform branch to buy a guarantee it does not need. `fdatasync` instead of `fsync` — rejected because the file is newly created, so its size and its blocks are both new metadata that `fdatasync` is not obliged to flush.
- **Rationale:** The two barriers buy different things and only one is load-bearing. Syncing the file before the rename is what makes the committed name always point at complete bytes — it converts "the previous revision survives a process crash" into "the previous revision survives a power loss", the class decision `[5]` argued about but did not cover. Skipping the directory sync bounds the guarantee honestly: the store promises that whatever `load` finds is whole, not that every `save` that returned is on disk. Both halves are stated in § Requirements § Durability bound and in § Goals rather than left implicit, because the earlier draft argued write-then-rename as though it closed the whole failure class. The cost is one `fsync` per file per `save`, on a tool that saves at the pace a human answers interview questions; no scenario asserts it, because no test can cut power, so task 10 asserts the observable half — both handles are synced before the first rename — through the mock it already installs.
- **Promotes to ADR:** yes

### [11] The store fixes its own file modes rather than inheriting the umask

- **Decision:** Every directory the store creates is `0o700` and every file it creates is `0o600`. `mkdir(..., { recursive: true, mode: 0o700 })` covers the root and the session directory; each temporary file is opened with mode `0o600`, and `rename` carries that mode onto the target.
- **Alternatives:** Inheriting the process umask — rejected because the default `0o022` on Linux yields `0o755` directories and `0o644` files, so every account on the machine could read a user's unpublished product ideas, and the store would be handing that decision to a value nobody in chrysalyst sets. Setting the mode with `chmod` after the write — rejected because it leaves a window in which the file exists at the wider mode. Setting the mode only on `session.json` — rejected because the transcript names the same session and the directory name is the identifier.
- **Rationale:** chrysalyst is a local single-user tool whose whole subject matter is an idea its author has not published, so the store is the only writer and owes the narrowest mode that still works. Naming the mode at creation costs one option per call and removes an ambient input from the result. Four behaviours were verified against this Node build rather than assumed: `mkdir` with `recursive` applies the mode to every level it creates, not only the leaf; it leaves an existing directory's mode alone, so a second `save` does not re-tighten or loosen anything; `0o022` masks neither `0o700` nor `0o600`, so the umask cannot widen them; and `rename` preserves the source's mode, which is why the temporary file rather than the target is the one that carries it. The assertion lives on the envelope scenario, guarded on non-Windows in task 2, because Windows reports a mode that does not describe POSIX bits.
- **Promotes to ADR:** yes

## Review Findings

Task numbers in these entries name the numbering in force when each round was reviewed. `plan.md` § Implementation Tasks later split the adapter stream into five red-green pairs and renumbered it; old task 2 is now tasks 2 through 11, old task 4 is task 12, old task 5 is task 13, and old task 6 is task 14.

### [plan-review] `load`'s new rejection path was recorded nowhere at the port

- **Finding:** Round 1, `[COMPLETENESS_GAP]` BLOCKER. This plan makes `load` reject over a present-but-unreadable record, which changes the `SessionStorePort` contract for every implementation and every caller. The delta touched only the port's Background and its round-trip scenario, so after merge the port still read as one that never throws, and its doc comment still promised that a stale link "is an ordinary outcome, not a failure". M3 could call `load` unwrapped and meet an unhandled rejection in an HTTP route.
- **Direction change:** `platform/session-store-port`'s delta gains a `DELTA:NEW` scenario, `A stored session the implementation cannot read is a failure`, asserting the rejection, that `undefined` reports absence alone, and that `list` does not reject over what it cannot read. Task 5 now proves it with a third double in `packages/core/src/ports/ports.test.ts` whose backing map holds an unreadable marker, and amends the `load` doc comment in `packages/core/src/ports/session-store.ts`. The § Requirements "Port purity" row is relaxed to permit that doc comment: `tests/workspace.test.ts`'s `core declares no runtime dependencies and its non-test source imports none` reads the manifest's `dependencies` and the import specifiers of non-test files, both untouched by a comment. § Impact lists the doc comment as a third out-of-delta edit.
- **Promotes to ADR:** yes

### [plan-review] The port's serialisation clause could not fail and stated the constraint backwards

- **Finding:** Round 1, `[AMBIGUOUS_REQUIREMENT]` BLOCKER. The round-trip scenario's clause — "a second double that stores the session through a serialisation round trip MUST return the same domain state" — was unfalsifiable against the JSON-safe `DraftSpec` fixture task 5 paired it with, and read as a guarantee the store preserves state when the real constraint is the opposite obligation on the caller choosing `TState`.
- **Direction change:** The clause is deleted; `SessionStorePort round-trips a session` returns to its recorded form and the delta's scenario requirement is met by the preceding finding's `DELTA:NEW` scenario. The constraint moves to `adapters/filesystem-session-store` as `State the store cannot serialise does not survive the round trip`, whose `TState` nests a `Date` and which asserts the field returns as an ISO string while the envelope's own two timestamps return as `Date`. Task 5 is retargeted to the unreadable-marker double alone; the serialisation test belongs to task 2's adapter stream. Decision [8] is rewritten to say which fact each level records and why.
- **Promotes to ADR:** no

### [plan-review] `save` had no failure behaviour in any scenario

- **Finding:** Round 1, `[COMPLETENESS_GAP]` BLOCKER. Nine scenarios covered the happy path and both read policies; none said what `save` does or leaves behind when a write fails. The § Goals promise "a crash during `save` that cannot destroy the previous revision" — argued in a § Patterns row, a § Consequences row, a § Requirements row and decision [5] — had no scenario and no coverage row, so the plan would have recorded a guarantee it never demonstrated.
- **Direction change (superseded in part by the round-2 finding below):** `adapters/filesystem-session-store` gains `A save that fails leaves the previous revision loadable`, asserting that `save` rejects, the previous revision still loads with both timestamps unchanged, `list` still reports the identifier, and the directory holds no leftover temporary file. Meeting it forced a design correction: `save` now stages both temporary files and renames only after both are written, because renaming `session.json` as soon as it was written left a transcript failure half-committed and the previous revision unloadable. § Requirements gains a "Save failure" row fixing the cleanup (`rm(path, { force: true })` per staged file, never masking the original rejection) and a rewritten "Write order" row fixing serialisation before any filesystem call. Task 2 names two injections — a `TState` holding a `BigInt`, which fails before the store touches the filesystem, and a session directory turned read-only, which fails the temporary write and is guarded on the test not running as root. Decision [5] and the § Patterns and § Consequences rows are restated to match.
- **Promotes to ADR:** no

### [plan-review] The save-failure guarantee was unbounded and no test reached the cleanup path

- **Finding:** Round 2, `[COMPLETENESS_GAP]` BLOCKER. § Requirements § Save failure promised that a failed `save` leaves the directory holding exactly what the previous save committed, without qualification. Two-phase staging cannot deliver that at the last failure point: once `session.json` is renamed, a failed `transcript.md` rename leaves the new state beside the previous transcript, which is the very residue decision `[4]` licenses — so the plan forbade a state it elsewhere calls ordinary. Neither injection task 2 named reached the guarantee either. A `BigInt` state fails at serialisation and a `0o500` directory fails the first `writeFile` — verified to leave no file behind — so both stop before any temporary file exists. Both would therefore pass unchanged against the write-then-rename ordering this plan replaced, leaving the staging decision and the `rm(path, { force: true })` cleanup rule untested.
- **Direction change:** The guarantee is bounded in two sentences — a failure at or before the `session.json` rename commits nothing; a failure of the `transcript.md` rename leaves the new `session.json` beside the previous transcript and never the reverse. The scenario's `WHEN` is narrowed to a save that fails "before either file is renamed into place", so its scope matches the injections that prove it. A § Consequences row records that a failed second rename is not undone, names the residual window, and rejects a backup-copy rollback; decision `[5]`'s Rationale now claims a narrowed window rather than an eliminated one. Task 2 gains a third injection — `vi.mock('node:fs/promises', importOriginal)` rejecting the second file's write — which is the only test in the plan that reaches the cleanup path and the only one that can distinguish two-phase staging from the replaced ordering. The § Patterns claim that no test needs a mock filesystem is softened to name that one mock.
- **Promotes to ADR:** no

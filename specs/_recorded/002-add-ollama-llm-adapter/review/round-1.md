## Premortem

Three failure stories, each routed into the taxonomy below.

1. **M1 was recorded ✅ but the live tier never ran.** `ollama` is not on this machine's PATH and nothing listens on `127.0.0.1:11434`. Task 9 and the `Test (live)` checklist row are the only gates on the milestone's whole purpose — falsifying the mission's claim against a real model — and C2 (CI) is skipped, so no runner covers it either. M3's walking skeleton becomes the first real contact with a model, one milestone too late. → `[HIDDEN_DEPENDENCY]`.
2. **M4's CI turns red for a reason nobody attributes to M1.** A workflow sets `CHRYSALYST_LIVE_LLM: ""` in a matrix `env:` block. Task 5's guard reads `=== undefined`, so the empty string un-skips the live suite on a runner with no daemon. The `tests/workspace.test.ts` assertion that decision-log [3] calls an equivalent guarantee matches text only and cannot see the inverted predicate. → `[REQUIREMENT_CONFLICT]`.
3. **M6's setup gate gives the wrong instruction.** A user points `CHRYSALYST_LLM_BASE_URL` at a port serving valid JSON of an unexpected shape. `status` gets a `200 OK`, the narrowing guard rejects the body, and nothing in plan or spec says what the adapter returns. The gate shows "start your backend" to someone whose backend is running, or "pull a model" to someone pointed at the wrong port. → `[COMPLETENESS_GAP]`.

## Feasibility

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: `plan.md` § Implementation Tasks task 9; § Verification › Checklist row `Test (live)`; § Verification › Manual Testing rows 2, 4, 5, 6
- Issue: five verification steps require a running Ollama daemon with `llama3.2:3b` pulled, and the plan never establishes that the daemon exists. Verified on the target machine: `which ollama` → `command not found`, and `curl -s -m 3 http://127.0.0.1:11434/v1/models` returns nothing. The manual-testing table starts at `ollama serve`, assuming the binary is already installed; no task installs it, and no task pulls the model as a prerequisite of task 9 rather than as an optional manual check. Because decision-log [9] skips C2, no CI runner covers the gap either. The consequence is not a slow task — it is that M1's stated reason for existing (roadmap § Sequenzierungs-Strategie: "Das ist nur an einem echten Modell falsifizierbar") goes unmet while the plan reports green, since every other checklist row passes without a daemon by design.
- Fix: Add a task before task 9 in `plan.md` § Implementation Tasks: "Install Ollama, start `ollama serve`, run `ollama pull llama3.2:3b`, and confirm `curl -s http://127.0.0.1:11434/v1/models` returns a `data` array containing `llama3.2:3b`." Add that task to a new Group in § Parallelization ordered before Group D. In § Requirements add a row "Live-tier prerequisite | An Ollama daemon with `llama3.2:3b` pulled MUST be present before task 9; the plan MUST NOT be reported complete on hermetic tests alone." If the user declines the install, add a decision-log entry recording that the live tier ships unexecuted and that M1's feasibility statement is deferred to M3.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: `decision-log.md` § [1] (marked **Promotes to ADR: yes**); `plan.md` § Impact
- Issue: decision [1] argues the roadmap's "Kein Cloud-LLM-SDK" guardrail is satisfied because `@ai-sdk/openai-compatible` "contains no OpenAI endpoint or credential". It never mentions that `ai@6.0.277` itself depends on `@ai-sdk/gateway@3.0.189` (verified: `npm view ai@6.0.277 dependencies`), Vercel's hosted-inference client, which `ai` uses as the default provider whenever a model is named by bare string instead of a provider instance. `plan.md` § Impact says contributors "gain three runtime dependencies" without noting the cloud client arriving transitively. Nothing in the spec deltas forbids a bare-string model. The mission constrains this directly: "Netzzugriff nur für die optionale LLM-Websuche und für Modell-/Backend-Downloads". Since decision [1] becomes the ADR that answers this exact guardrail question, an ADR silent on the one cloud client in the tree is incomplete.
- Fix: Extend `decision-log.md` § [1] § Rationale with: "`ai@6` depends on `@ai-sdk/gateway`, Vercel's hosted-inference client, which `ai` resolves only when a model is passed as a bare string. The adapter always passes the instance returned by `createOpenAICompatible(...)`, so no gateway endpoint is reachable." Add a `plan.md` § Requirements row: "Provider binding | Every `generateText` and `streamText` call MUST pass a model instance from `createOpenAICompatible(...)`, never a bare model-id string."

#### [EFFORT_MISESTIMATION] ADVISORY
- Location: `plan.md` § Implementation Tasks task 2; § Dependencies observation table
- Issue: task 2 is one line covering four distinct fixtures — a chat-completion JSON body, an SSE delta sequence, two model-list bodies, and an `ECONNREFUSED` rejection — plus a request recorder, plus the eight hermetic scenarios that consume them. The SSE fixture is the risky one: the stub must emit the exact `text/event-stream` frames that `@ai-sdk/openai-compatible@2.0.74`'s response schema accepts, including the `[DONE]` sentinel and the envelope fields that schema validates. § Dependencies claims every listed API observation "was executed against those exact versions rather than recalled", yet the table records no SSE frame shape — the single observation task 2 most depends on. If the assumed shape is wrong, eight of ten scenarios stall behind reverse-engineering the provider's parser.
- Fix: Add a row to `plan.md` § Dependencies observation table recording the verified SSE frame the v2 provider accepts (headers plus one literal `data:` line and the terminator), captured from a real run. Split task 2 in § Implementation Tasks into "2a. Build the `fetch` stub and request recorder with the four response fixtures, proving the SSE fixture drives `streamText` to yield two chunks" and "2b. Write the eight hermetic scenarios as failing tests against that stub", and update § Parallelization Group B to `2a → 2b → 3 → 4`.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `plan.md` § Implementation Tasks task 5 vs. § Requirements row "Environment" and `decision-log.md` § [3]
- Issue: two lines of the same plan specify different gates. § Requirements says "`CHRYSALYST_LIVE_LLM` (any non-empty value enables the live tier)" and decision [3] repeats "Any non-empty value enables the tier". Task 5 dictates the concrete predicate `describe.skipIf(process.env.CHRYSALYST_LIVE_LLM === undefined)`. An empty assignment — `CHRYSALYST_LIVE_LLM=` in a shell, or `env: { CHRYSALYST_LIVE_LLM: "" }` in a workflow, both idiomatic ways to leave a flag off — yields `''`, not `undefined`, so task 5's guard *enables* the tier where the requirement disables it. The failure lands on a runner with no daemon, which is precisely the outcome the tier exists to prevent and the pattern decision [3] hands to M4. Task 6's enforcement cannot catch it: a text match for `CHRYSALYST_LIVE_LLM` inside a `skipIf` passes for any predicate, including an inverted one. Decision [3]'s claim that "a static assertion over the file's text buys the same guarantee" as running the suite is therefore false for this defect class.
- Fix: Replace the guard in `plan.md` § Implementation Tasks task 5 with `describe.skipIf((process.env.CHRYSALYST_LIVE_LLM ?? '') === '')` so an empty value skips, matching § Requirements. Add a `<!-- DELTA:NEW -->` scenario to `specs/_plans/add-ollama-llm-adapter/adapters/ollama-llm-adapter/spec.md` — "Scenario: An empty live-tier flag leaves the tier disabled" — asserting that an unset variable and an empty-string variable both skip the live suite while any non-empty value enables it, and add the matching row to `plan.md` § Verification › Scenario Coverage.

#### [COMPLETENESS_GAP] BLOCKER
- Location: `adapters/ollama-llm-adapter/spec.md` § "Status reports a reachable backend and its model inventory"; `plan.md` § Requirements rows "Status transport" and "JSON narrowing"; `decision-log.md` § [4]
- Issue: `status` is specified for four outcomes — reachable with models, reachable with none, unreachable, cancelled — and one reachable outcome is missing: a `200 OK` whose body parses as JSON but fails the narrowing guard. § Requirements covers "Any thrown error other than an abort" and "a non-`ok` response", neither of which fires here; `response.json()` succeeds and the guard simply returns false. The spec names no result, so no pass/fail test can be written for that branch today. This is not hypothetical for this adapter: `plan.md` § Decision advertises pointing the same module at LM Studio and llama.cpp, and Ollama itself answers some conditions with a `200` error envelope. It also breaks a claim the plan makes about itself — decision [4] states `{ available: true, models: [] }` "is a different fact and stays distinguishable", a distinguishability the specification does not secure.
- Fix: Add a fifth `THEN` clause to `adapters/ollama-llm-adapter/spec.md` § "Status separates an unreachable backend from a cancelled probe": "*AND* a backend answering `200` with a body the model-list guard rejects MUST report as unavailable with an empty model list, because a body the adapter cannot read is not evidence the backend can serve a request". Add the matching sentence to `plan.md` § Requirements row "Status transport" and to `decision-log.md` § [4] § Decision, and extend the `resolves unavailable for a refused connection and rejects a cancelled probe` test name in § Verification › Scenario Coverage to cover the malformed-body case.

## Task Breakdown

#### [TRACEABILITY_GAP] ADVISORY
- Location: `platform/monorepo-workspace/spec.md` § "Live-tier tests are gated by an environment flag", third `AND` clause; `plan.md` § Verification › Scenario Coverage
- Issue: the scenario's third assertion — "a run of `pnpm -r --include-workspace-root test` without that variable MUST report those tests as skipped rather than failed" — is a behavioural claim about a test run. The single mapped test (`every live test file gates on CHRYSALYST_LIVE_LLM and awaits nothing at module scope`) is a static text scan and verifies the first two clauses only. Decision-log [3] explicitly rejected the mechanism that would verify the third ("Asserting the skip behaviour by meta-testing a Vitest run — rejected as slow and brittle; a static assertion over the file's text buys the same guarantee"). It does not buy the same guarantee, as the `=== undefined` blocker above demonstrates. The clause is verified only by a § Manual Testing row, so a permanent library scenario carries an assertion no automated test defends.
- Fix: Either delete the third `AND` clause from `platform/monorepo-workspace/spec.md` and move it to `plan.md` § Verification › Manual Testing as its own row, or keep it and add a `plan.md` § Verification › Scenario Coverage row mapping it to a second assertion in `tests/workspace.test.ts` that evaluates each file's guard expression against `''`, `undefined`, and `'1'`. Update `decision-log.md` § [3] § Rationale to drop the "buys the same guarantee" claim either way.

#### [COMPLETENESS_GAP] ADVISORY
- Location: `plan.md` § Implementation Tasks task 6
- Issue: two mismatches between the task and the scenario it implements. First, the spec requires "each file MUST NOT contain a top-level `await`"; task 6 implements "contains no line beginning with `await`", which passes for `const models = await llm.status();` and `for await (const chunk of llm.stream(...))` at module scope — the exact constructs a live test would use, and the ones that make collection contact a backend. Second, "Reuse the suite's existing file-reading helpers" does not hold: the only walker in `tests/workspace.test.ts` is `nonTestSourceFiles`, which is restricted to `<pkg>/src` and skips every `*.test.ts` file by name, so it cannot find a `*.live.test.ts` at all. Only `readText` is reusable; task 6 needs a new walker it does not budget for.
- Fix: Reword `plan.md` § Implementation Tasks task 6 to: "Add the `Live-tier tests are gated by an environment flag` assertion to `tests/workspace.test.ts`. Generalise `nonTestSourceFiles` into a walker parameterised by filename predicate and root (the current call site keeps its behaviour), use it to collect every `*.live.test.ts` in the workspace, and assert each file names `CHRYSALYST_LIVE_LLM` inside a `skipIf` and contains no module-scope `await` — matching `await` and `for await` at zero indentation, not only line-initial `await`."

## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: `decision-log.md` § [5] (marked **Promotes to ADR: yes**); `plan.md` § Implementation Tasks task 4
- Issue: decision [5]'s rationale asserts "The cheapest honest form of that is a module that never mentions Ollama in its logic — proved by a scenario that drives it against a non-Ollama base URL". Task 4 then puts `llmConfigFromEnv` — carrying Ollama's port `11434` and Ollama's model id `llama3.2:3b` — inside that same module, and `adapters/ollama-llm-adapter/spec.md` § "Ollama's defaults come from the environment" pins both constants to it. The scenario proves the *request paths* are backend-neutral; it proves nothing about the module's identity, because the defaults never travel over the wire. The result is one module owning two decisions with different reasons to change: how an OpenAI-compatible endpoint is spoken, and which backend chrysalyst assumes by default. When M6's setup gate or a later LM Studio default arrives, the second decision has to move, which is the unpicking decision [5] claims parameterisation avoids. `specs/mission.md` § Architecture independently names "je ein Adapter für Ollama, llama.cpp und LM Studio hinter `LlmPort`"; decision [5] argues against a per-backend layer using the roadmap alone and never reconciles that with the mission, even though it is ADR-bound.
- Fix: Soften `decision-log.md` § [5] § Rationale — replace "a module that never mentions Ollama in its logic" with "a module whose request behaviour is backend-neutral; the Ollama defaults live in `llmConfigFromEnv` and are the one Ollama-specific thing in the file" — and add a sentence stating that a second backend's defaults will be added as a sibling resolver in the same module, not a second adapter, so the mission's "je ein Adapter" reads as one adapter *instance* per backend. Add that reconciliation to `plan.md` § Decision › Patterns row "Generalisation by parameter, not by layer".

## Prose Quality

#### [PROSE_UNCLEAR] ADVISORY
- Location: `plan.md` § Decision (lines 42, 52), § Consequences, § Requirements row "Model spec version"
- Issue: "the SDK" names two different packages across the document, violating the one-term-per-concept rule where it costs the most — in normative rows. Line 42 "the SDK's provider interface has no list-models method" means `@ai-sdk/openai-compatible`; line 52 "The SDK accepts a `fetch` override" means the `createOpenAICompatible` factory; § Consequences "`maxRetries: 0` | The SDK default of 2" means `ai`; "rewrap the SDK error" means an error class exported by `ai`. An implementer resolving a Requirements row has to guess which package a statement constrains, and the two are pinned to different major lines on purpose.
- Fix: In `plan.md`, replace each "the SDK" with the package it names — `ai` or `@ai-sdk/openai-compatible` — or introduce the collective term once in § Decision › Architecture ("`ai` and `@ai-sdk/openai-compatible`, together *the SDK pair*") and use only the specific package name in § Consequences and § Requirements.

## Feasibility

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: `plan.md` § Implementation Tasks task 9; § Parallelization Group D; § Requirements row "Live-tier prerequisite"
- Issue: task 9 reads "Install Ollama, start `ollama serve`, run `ollama pull llama3.2:3b`" and names no method, no privilege, and no prerequisite. On the target machine that task cannot run unattended, and both blockers were verified rather than assumed. First, `sudo -n true` answers "sudo: a password is required", while the official installer at `https://ollama.com/install.sh` sets `SUDO="sudo"` whenever the caller is not root and uses it for every step (`$SUDO install -o0 -g0 -m755 -d $BINDIR`, `$SUDO tar -xzf - -C "${dest_dir}"`). A `curl … | sh` from a non-interactive agent shell therefore fails or hangs on a password prompt. Second, the current release (`v0.33.3`) publishes `ollama-linux-amd64.tar.zst`, and `zstd` is absent here (`which zstd` → not found); the script's own failure text is "Debian/Ubuntu: sudo apt-get install zstd", which needs the same password. § Parallelization compounds it by describing Group D as an ordinary task group — "touches no repository file and depends on no other group; start it at any point" — so nothing tells `/speq:implement` this is the one step a human must run. Because § Requirements "Live-tier prerequisite" makes the whole plan's completion depend on Group D, an unexecutable Group D leaves the milestone's stated purpose unreachable, which is the same end-state round 1 blocked one level up. Disk is not a constraint: 948 GB free.
- Fix: Rewrite `plan.md` § Implementation Tasks task 9 as: "**Human step.** Install Ollama on the development machine. The official installer needs root and `zstd`, neither of which is available unattended here: install `zstd` first (`sudo apt-get install -y zstd`), then run `curl -fsSL https://ollama.com/install.sh | sh` in an interactive shell. Start the daemon (`ollama serve`, or `systemctl --user`/`sudo systemctl start ollama` if the installer registered a unit — systemd is running on this host), run `ollama pull llama3.2:3b` (≈2 GB), and confirm `curl -s http://127.0.0.1:11434/v1/models` returns a `data` array containing `llama3.2:3b`." In § Parallelization, label Group D "Group D (human step — the implementer MUST stop and ask, never pipe the installer into a non-interactive shell)". Add a `decision-log.md` § Review Findings entry recording that task 9 is executed by the user, not by an implementation agent, and that Group E blocks until the user confirms the `curl` output.
